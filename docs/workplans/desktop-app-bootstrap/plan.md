## Objective

Deliver a runnable macOS + Windows desktop application with the approved OpenCode v2 server packaged and supervised as an app-owned sidecar. Electron is now explicitly selected by the user after the reviewed shell comparison. **Status:** dependent contracts are reconciled and reviewed, exact-set packet r1 is approved and recorded, and its bounded compatibility probes/bootstrap may proceed under the exclusions below. ## Authorized and frozen product boundaries

- User confirms the product is an installed desktop app for macOS and Windows; preserve the complete PRD F-01–18 product goal.
- Electron, Tauri 2, and Neutralinojs were compared against a common macOS/Windows + app-owned OpenCode `serve` matrix. The user explicitly selected Electron on 2026-09-28. Keep the comparison and alternatives in ADR-0002, record Electron as the selected decision, and reconcile all dependent contracts to Electron. Do not let browser renderer/bridge evidence stand in for Electron desktop evidence.
- Package and directly supervise the OpenCode v2 `serve` sidecar as an app-owned foreground process. Do not adopt an ambient/shared service, expose its local HTTP credentials to the renderer, or substitute an embedded SDK host without a reviewed plan change.
- Use synthetic workspaces and disposable configuration for the first sidecar vertical slice. Do not read existing user configuration or credentials, add external telemetry, enable real project mutations, or persist personal data.
- No public distribution, signing/notarization, auto-update service, app store, provider auth, or external release.
- Renderer has the selected shell's strongest supported isolation settings and a named, typed, least-authority API; no raw IPC, shell, filesystem, child-process, OpenCode HTTP credentials, or unrestricted bridge authority. This bootstrap introduces no preview surface; when preview is implemented, it must receive no privileged API or sidecar credential and must pass its own isolation gate.

## Risks and stop conditions

- Existing browser pairing/CORS tests do not prove app-owned OpenCode sidecar lifecycle, desktop IPC, service authentication, or OS isolation. Preserve them only as browser-boundary evidence.
- Electron/server-client package compatibility, per-OS sidecar assets, registry/cache availability, and Windows runtime access remain unverified until the approved architecture probes run.
- A renderer displayed inside a desktop shell is not by itself proof of production-ready UI, platform support, sidecar integration, or completion of the full product.
- macOS and Windows package formats and unsigned local launch behavior must be observed; do not infer signing/notarization or Windows behavior from a macOS cross-build.
- Any need to read existing user credentials/configuration, access user data, contact an unapproved service, or publish a release stops this increment and returns to plan/user scope. OpenCode sidecar execution uses only the pinned app-owned binary and a disposable synthetic workspace.
