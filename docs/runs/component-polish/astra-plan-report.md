## Judgment and architecture

Proceed within the five-family scope. This is a repair of component contracts and their Figma projection, not a new visual system or application implementation. Preserve the exact 44 canonical variants, including all 18 accepted Button variants, and demonstrate composed states outside the canonical variant inventory.

The main architectural gap is that content and state semantics are explicit while layout, nested composition, and border visibility remain implicit. Add small structured fields to the existing component contract rather than a second schema or generic component engine: sizing/alignment, feedback precedence, stroke visibility, nested component reference, action availability, and result-target availability. Keep the token hierarchy and generator. Do not change global surface, radius, or Button tokens to solve a local component issue.

Use five compositions:

- **Input:** a vertical, content-height field group containing label, a 40px control shell, and one feedback slot. Ring geometry belongs to the control, not the entire field group. Error replaces the ordinary hint; error+focus preserves error semantics and adds the existing outer ring.
- **StatusBadge:** a reusable 24px-high, text-hug pill with 8px horizontal padding and vertically centered single-line text. Nested badges use the same geometry. Permission status labels may override badge text/tone explicitly; an approved permission must remain neutral/info, never inherit execution-success meaning.
- **NavigationItem:** a 40px row filling its parent width, with 12px start padding and start-aligned label. Focus is an independent overlay on default/selected state. Prefer a restrained persistent non-color selected cue, such as medium label weight or a compact current marker, if fills alone remain ambiguous; do not restore a decorative stripe.
- **ToolCall:** a quiet summary with tool/status first and source/target/result metadata below as needed; an optional expanded evidence area supplies grouping only when it is actually shown. Specify `summary` stroke as absent and detail boundary separately. Retain existing border binding for the functional detail region, rather than deleting the token or drawing it on every summary.
- **PermissionRequest:** retain one restrained scope boundary, exact scope/destination, and independent decision status. Actions are actual instances of accepted Button components; use primary for allow and quiet for deny/refresh. Do not create custom action frames or danger styling merely because an action says deny.

## Decisions to make explicit before implementation

1. **40px visual Button versus 44px target:** retain the existing Button appearance and instance geometry. Specify a minimum 44px interactive allocation around each instance (2px above/below a 40px control), with at least 8px between target rectangles. A decorative outer Figma frame alone is not proof of a working hit target: annotate the allocation and require the future renderer's actual actionable hit region to include it, without a second nested focusable control. Keep labels centered and focus rings fully visible. Do not claim runtime hit testing from Figma.
2. **Evidence action:** distinguish local expansion from navigation. A disclosure is a keyboard-operable action with expanded state; a result navigation action uses a runtime-supplied safe destination/result identifier. Expose “근거 보기” only when a valid target exists, or show clear non-actionable unavailable text. Label, focus treatment, and visible link/disclosure cue must distinguish it from metadata. Never invent a destination URL or attach a placeholder `#` link. Figma can demonstrate expansion to a real local example and document the future result-target contract; that is not a live result link.
3. **Sending state:** current text says both decisions are disabled while `visual.actions` is empty. Resolve this source ambiguity before Figma work. Recommend retaining both Button instances in their disabled form while showing “결정 전송 중”, preserving layout and suppressing duplicate decisions. Use a loading Button only when the triggering decision is explicitly known; do not imply that allow was selected. Approved/denied need status, not active decisions; stale exposes only enabled refresh.
4. **Specification gate order:** revise canonical JSON and documentation as the specification increment, register their real hashes, then obtain the independent design-spec pass and handoff before projecting them into Figma. Reviewing the unchanged old contract before writing the new layout contract would not authorize the new design. Replace `pending` document hashes and reconcile declared document versions with the actual artifacts. `system.md` should identify this current run without erasing historical provenance.

## Source versus Figma and verification

**Repository:** encode feedback precedence, dimensions/hug/fill rules, alignment, optional detail strokes, nested Button/Badge references, composed-state requirements, and action/result availability in `components.json`; explain behavior and state mapping in `system.md`. Modify `manifest.json` only for a demonstrated missing or unsuitable token. Regenerate CSS through the existing generator if token changes require it. Preserve the Button subtree byte-equivalent after normalized serialization, and record its unchanged fingerprint.

**Figma:** apply the reviewed contract to base components first, then existing examples; correct auto-layout rather than compensating with absolute offsets. Use nested instances, correct text auto-resize, controlled content/fill width, and explicitly managed focus overflow. Add error+focus and selected+focus examples in both modes without adding base variants. Inspect nested instance overrides so old fixed dimensions or obsolete text do not survive a master correction. Make changes one page per call as planned; do not publish or change access.

**Required evidence:** retain `validate_system.py`, but add a targeted run-local structural check registered in `contract.json` for the new measurable rules and Button preservation. The existing validator checks inventory, aliases, CSS, contrast, and only some state relationships; it does not inspect Figma node types, hug sizing, action references, overlap, or screenshot quality. Validate Figma through a node/bounds/binding export plus rendered captures and independent visual judgment. State the remaining limit plainly: design-library readiness is achievable here; keyboard, assistive-technology, browser zoom, hit testing, and runtime link behavior remain future application verification and must not be reported as passed.

## Principal risks

- Fixing only Figma reproduces drift at the next synchronization; fix the canonical contract first.
- Flattening outlines without distinguishing evidence actions removes affordance; preserve action semantics and visible cues while removing only decorative summary borders.
- Fixed field-group heights or inherited badge overrides can leave the original overlap in examples even after correcting base components; verify both levels.
- Approval-tone reuse can accidentally communicate execution success; assert labels and neutral approved tone separately from ToolCall status.
- A global token adjustment can silently alter accepted Buttons; compare Button definitions and resolved bindings before/after, not only variant counts.
- Static checks and attractive captures cannot establish actual runtime behavior. Report exact verified scope rather than an unqualified production-runtime claim.
