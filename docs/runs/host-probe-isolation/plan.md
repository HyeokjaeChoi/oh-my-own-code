# Host probe isolation preflight

Revision: 6 · 2026-09-28 · Status: proposed; no canary code may execute until an independent static preflight code/security review passes.

## Confirmed outcome

Establish whether this macOS host can enforce and independently evidence an OS-level containment boundary suitable for one future `@opencode/sdk@2.0.18` embedded-host lifecycle probe. This run builds and executes SDK-free sandbox canaries only. It never imports, instantiates, starts, or attaches to OpenCode, never reads user configuration or secrets, and never contacts an external service. If the canary boundary cannot be enforced, the result is `NO-RUN` for the real SDK and the current build-delivery run remains active.

## Requirements and inputs

- Preserve `docs/runs/build-delivery/plan.md` revision 7 (SHA-256 `7bcacee7766d65c157a9b1e8b402f9a77e792f6907c89a045b084a62546999d3`) as the broader project SSOT.

## Scope

- Implement a disposable SDK-free preflight harness under `spikes/host-probe-isolation/` that resolves and records the exact runtime executable, creates a unique temporary fixture root with restrictive permissions, launches narrowly-scoped canaries through `sandbox-exec`, bounds time/output, validates expected allow/deny behavior, and removes only its owned fixture root. Use both the harness's independent command watchdog (`check --timeout 60`, process-group termination, 8 KiB per output stream) and a source-pinning supervisor with a 45-second worker deadline, 16 KiB aggregate output ceiling, and five-second reap window.
- The reviewed entrypoint is the exact installed Node executable `/opt/homebrew/Cellar/node/26.8.2/bin/node`, SHA-256 `902b6a6984d5d825829ea9064ab73b734548df37bc0683990dca31c8dc2a9253`. Launch it through `/usr/bin/env -i` with only literal `LANG=C`, `LC_ALL=C`, and `NO_COLOR=1`; the verifier checks its own `process.execPath` and binary digest before any worker start. An identity mismatch is `BLOCKED`.
- Before creating fixtures/listeners or running any canary, require an audited exact read-only runtime dependency closure for the child. If it cannot be established from frozen, locally available inputs, report `NO-RUN` with every canary `unverified`; do not try the profile speculatively. Broad package-store, `/System`, and `/usr/lib` subtree read rules are prohibited; only exact audited dependency paths may be granted.
- Test only synthetic filesystem sentinels and loopback-only socket operations. Never attempt a routed, public, documentation-range, DNS, or other external destination; this preflight cannot establish general egress denial by sending packets. The runner must not read user files or environment values; child variables are constructed from literal values.
- The supervisor may start one loopback-only listener bound to `127.0.0.1` on an ephemeral port. It accepts no application payload, closes any accepted connection immediately, and is closed in `finally`. The sandboxed child tests connection denial against that exact owned listener and separately tests denied listener creation. If an unexpected connection succeeds, the supervisor immediately closes the accepted socket and child connection, records `unexpected_allowed`, and fails closed.
- Preserve the exact sandbox profile and canary evidence as reviewable artifacts. Clearly distinguish observed syscall/policy behavior from guarantees that this preflight cannot prove.
- The check passes when the harness safely evaluates the matrix, emits a truthful `READY_FOR_REVIEW` or `NO-RUN` outcome, and verifies cleanup. A `NO-RUN` result is not a containment pass. The check fails and the run remains blocked if runner integrity, bounded execution, evidence integrity, or cleanup cannot be established.
- Never make routed network probes. A loopback denial provides evidence only for the tested local TCP operations. General external egress, UDP, DNS, IPC, and untested facilities remain unverified unless the platform policy and independent enforcement evidence establish them without sending external traffic; otherwise the real-host decision is `NO-RUN`.

## Out of scope

- Any import or execution of `@opencode/sdk`, `@opencode/client`, a host binary, a real or ambient OpenCode service, provider, MCP, shell, PTY, browser, session, workspace, plugin, project data, or user configuration.
- Creating a reusable real-host runner, changing production bridge/browser behavior, installing dependencies, probing online destinations, and claiming the SDK is safe or isolated.
- Approving the later real-host lifecycle probe. It requires a separate explicit user approval after the concrete runner, effect manifest, hashes, independent code/security review, and SDK-free canary evidence are available.

## Acceptance criteria

1. **HPI-1 Runtime and filesystem root:** both branches verify the exact Node executable path and digest and launch the entrypoint through a literal clean environment, without inherited Node loader or path settings. Only if the exact read-only runtime dependency closure is audited may the runner create a canonical, unique root with no symlink traversal, owner/mode checks, immutable input area, and owned scratch, then construct a clean child environment from an explicit literal allowlist and record names only, never values. If the closure is not audited, it must stop before fixture, listener, child environment, or canary effects; record the specific prerequisite as unverified and all seven controls as unverified, and verify that no owned resources were created or require cleanup. Do not label unexecuted root/environment protections verified.
2. **HPI-2 OS isolation controls:** safely evaluate the recorded profile and supported enforcement scope. Record each claimed control as `verified`, `unavailable`, `failed`, or `unverified`; report no containment pass for failed/unavailable/unverified controls. `READY_FOR_REVIEW` is allowed only when every required control passes; otherwise choose `NO-RUN`. Do not equate successful evaluation with successful containment. Before canaries, require an exact audited runtime dependency closure; if it is unavailable, no canary launches and all seven controls remain `unverified`. Bind verification to the exact source bytes that are subsequently evaluated or passed as input; reject path rereads that could change between hashing and use. Bound execution with the outer harness watchdog and the source-pinning worker supervisor.
3. **HPI-3 Canary evaluation and decision:** when the runtime dependency precondition is verified, safely evaluate exactly two positive and five negative controls. Positive controls are reading the exact immutable synthetic input and writing one owned scratch sentinel. Negative controls are (a) reading a pre-existing owner-readable sentinel outside all child read roots, (b) writing a pre-existing synthetic writable file outside child write roots, (c) binding/listening on loopback, (d) connecting without payload to the supervisor-owned loopback listener, and (e) spawning the exact existing runtime executable with a harmless fixed argument. Verify each target exists and is otherwise accessible to the parent; require the expected sandbox-denial class, not generic failure. Record each actual result as `verified`, `unavailable`, `failed`, `unverified`, or `unexpected_allowed`. If the prerequisite is unavailable, report all seven as `unverified` and choose `NO-RUN` before fixture/listener/canary effects. A truthful `NO-RUN` check may exit 0 because the preflight decision was safely evaluated; that exit does not mean any containment control passed. No SDK/client import or host operation occurs.
4. **HPI-4 Cleanup and evidence:** timeout/failure paths are bounded; unexpected successful child/socket operations have exact owned handles and immediate closure/termination; only the exact owned root is removed after child exit; the machine-readable report contains no secret, raw environment value, user path, SDK response, or unbounded stderr. An independent static code/security review passes before the first canary; an independent final code review assesses exact source plus resulting evidence.
5. **HPI-5 Real-host hold:** the preflight terminates in one of two truthful decisions. `READY_FOR_REVIEW` requires every required positive and negative control to pass with attributable evidence, cleanup to pass, and no untested claim to be promoted. `NO-RUN` is a valid completed investigation when any required control is unavailable, unverified, ambiguous, unexpectedly allowed/denied, or the sandbox is unsupported, provided cleanup itself is verified; the report lists actual outcomes and leaves containment unverified. Cleanup failure remains unresolved/blocked and cannot finish. Neither decision executes the SDK or authorizes a later host startup; that requires separate explicit approval tied to the reviewed real-host effect manifest.

## Verification

- Required check: `isolation-canaries`, the exact command `python3 .solopreneur/harness.py check host-probe-isolation --name isolation-canaries --timeout 60`. Its contract argv runs `/usr/bin/env -i LANG=C LC_ALL=C NO_COLOR=1 /opt/homebrew/Cellar/node/26.8.2/bin/node spikes/host-probe-isolation/verify.mjs`, clearing inherited environment before Node starts. The harness applies an independent 60-second process-group watchdog and captures no more than 8 KiB per output stream. `verify.mjs` verifies its exact runtime identity, pins worker/canary/profile bytes, executes the verified worker source in memory, and supervises it with a 45-second deadline, 16 KiB aggregate output ceiling and five-second reap window. The worker uses the same verified buffers for profile/report generation. If exact runtime dependencies are not audited, it returns `NO-RUN` before fixture, listener or sandbox effects, with all controls unverified. Otherwise the declared effects are a short-lived `sandbox-exec` Node child, one supervisor-owned loopback listener and zero-payload local connection attempt, synthetic files under one exact `/private/tmp` fixture root, and deletion of that owned root. It makes no routed/external network attempt and imports no SDK code.
- Operation matrix: (1) allowed read from immutable input; (2) allowed write under owned scratch; (3) denied read from a pre-existing synthetic readable file outside all child read roots; (4) denied write to a pre-existing synthetic writable file outside child write roots; (5) denied loopback bind/listen; (6) denied zero-payload connect to the exact supervisor-owned loopback listener; (7) denied child execution attempt against the exact resolved Node binary. If any unexpected operation succeeds, immediately close/terminate its exact owned resource and report `unexpected_allowed`. Never scan or kill unrelated processes.
- Require each real target to exist and be accessible to the unsandboxed supervisor, and bind an observed failure to the exact operation, errno/denial event, and target class. Missing, invalid, refused, timed-out, or generic failures are `unverified`, not sandbox denials. Avoid exposing raw target paths in exported output.
- Record actual OS/runtime version, binary identity, profile hash, fixture root identity (redacted to a stable class/count in exported evidence), child exit/timeout, each operation outcome, denials, and cleanup. Do not claim general egress enforcement or sandbox certification from local TCP evidence alone.
- Before first canary execution, a fresh reviewer must statically review the exact launcher, profile, canary bodies, allowed effects, failure behavior, time/output budgets, and cleanup against frozen hashes. Run only those reviewed hashes. Afterward obtain a fresh independent final code review bound to source and canary evidence.
