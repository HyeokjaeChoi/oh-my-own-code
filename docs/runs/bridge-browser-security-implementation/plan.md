# Loopback browser pairing and read-only admission

Revision: 11 · 2026-09-28 · Status: proposed

## Confirmed outcome

Implement the approved browser-to-local-bridge contract v0.4 for the current synthetic workbench. The UI can manually pair with the user's locally running bridge and then read only its synthetic snapshot/events. Keep domain mutations, SDK calls, file/process operations, persistence, and external services disabled.

This is one implementation increment in the larger `build-delivery` objective, not product completion. The SSOT for this bounded increment is this plan and `contract.json`; its normative implementation contracts are `docs/design/specs/browser-bridge-security.md` v0.4, `docs/design/specs/bridge-pairing-client-contract.md` v0.8, `docs/design/specs/workbench-ux.md` v0.3, `docs/design/system.md`, and `docs/design/components.json`. For the listed API routes in this increment, client-contract v0.8 supersedes the parent security spec's generic processing order and illustrative status mappings; all other security controls and effect limits remain binding. This run does **not** complete the parent security spec's BB-01..10 verification matrix, its runtime handler/effect-counter requirements (including BB-02 and BB-09), production/browser scenarios, or OS isolation. Here, synthetic-state equality assertions and static review for absent SDK/filesystem/process-execution call sites are bounded evidence only; parent zero-effect requirements remain binding and the broader counter-based evidence is pending a separately scoped run.

## Scope and decisions

- Apply exact loopback peer and Host checks, duplicate-security-header rejection, exact configured trusted-Origin matching, deterministic request-validation precedence, response-decoration-only security checks, and route-specific `Sec-Fetch-Site` rules from the v0.4 contract and its v0.8 client-contract supplement. For Origin-present API/preflight/control requests, permit only `same-origin` or the explicitly allowlisted dev-origin `same-site` value; missing, malformed, duplicate, `cross-site`, or `none` fails closed. Preserve only the specified production same-origin read omission exception.
- Implement exact routes and request/response schemas from `bridge-pairing-client-contract.md`: `POST /api/v1/pair`, `POST /api/v1/pair/revoke`, `POST /api/v1/pair/heartbeat`, `GET /api/v1/snapshot`, `GET /api/v1/events`, and credential-free `OPTIONS` preflight for declared routes. Enforce its 4 KiB JSON body limit, 43-character base64url secret encodings, fixed safe error envelope, exact HTTP status mapping, and exact route-specific preflight method/header allowlist. After status selection, perform decoration-only Host/Origin/Fetch-Metadata validation: exact trusted-Origin plus valid Host/metadata receives ACAO+Vary even for early 400/404/405; rejected host/origin/metadata remains status/body-opaque to browser JS. This increment registers no mutation route: all unlisted legacy/domain/mutation API paths uniformly return `404 NOT_FOUND`; registered paths with unsupported methods return `405 METHOD_NOT_ALLOWED`; WebSocket upgrades are closed.
- Pairing uses a 256-bit CSPRNG one-time code printed by the interactive bridge launcher. The process accepts a literal `pair` terminal command to issue another code without restarting the bridge; this replaces only the unconsumed code and leaves existing capabilities active, so another tab can pair while current tabs remain connected. Store only the code digest in memory, allow five attempts for its 120-second lifetime, atomically consume once, and issue one 256-bit read-only per-tab capability. Tests may inject deterministic codes and call the in-memory issuer through a test factory only; never use an environment variable, argv, URL, bundle, persistent browser storage, or captured production log for test setup.
- Store capability digests only in memory; apply 15-minute idle and 8-hour absolute expiry, 5-minute UI heartbeat, per-tab revoke, and bridge-epoch invalidation. Streaming is not implemented in this increment; `/api/v1/events` returns the finite synthetic event list only. WebSocket remains disabled.
- Configure the current dev UI origin `http://127.0.0.1:4200` with bridge origin `http://127.0.0.1:4318`; E2E uses UI `http://127.0.0.1:5420` and bridge `http://127.0.0.1:5318`. Make browser requests directly to bridge with `credentials: "omit"`; remove the Vite proxy so it cannot obscure Host/origin boundaries. Each UI origin must be in the bridge's explicit startup allowlist. Add trusted-UI `frame-ancestors 'none'` response policy. In a same-origin production deployment, bridge origin may default to `window.location.origin`; no production asset server is added here.
- Add the UI state/action/error transitions from `bridge-pairing-client-contract.md`: disconnected, pairing, rejected pair input, uncertain pair outcome, authenticated loading, connected, recoverable read failure, heartbeat failure, terminal capability-auth failure, revoking, and local disconnect with unconfirmed server revoke. Implement the exact operation/result mapping, including malformed pair `200` to uncertain outcome requiring fresh code; pair `401 BOOTSTRAP_INVALID` remains recoverable input rather than terminal capability auth; heartbeat success cannot erase a read error before refreshed data succeeds; revoke failures including `401` always clear local credentials and show unconfirmed server revoke. Clear the code before awaiting the request, suppress duplicate submit, keep capability only in component memory, abort requests/timers and suppress stale responses on disconnect, move keyboard focus when pending controls are disabled, and preserve explicit focus/error/announcement behavior. Do not add local/session storage or make real SDK/data claims.
- Remove the bridge HTTP `/health` readiness endpoint. Start the bridge in the in-process E2E fixture and use the test fixture's completed `listen` event to establish readiness; production exposes no unlisted health route.

## Regression closure matrix from independent code review

The five P2 findings in the earlier independent code-review handoff and two new P2 findings in `code-review-r2.json` are preserved below as concrete behaviors and checks:

| Finding | Owner | Required behavior | Required evidence |
|---|---|---|---|
| Initial-read disconnect was a no-op while `operationRef` remained `pair` | Frontend engineer; test engineer owns E2E | As soon as a valid capability is accepted, Disconnect is actionable even while the initial snapshot/events read is pending. Disconnect clears local capability, aborts reads, increments the generation and prevents late success from reconnecting the tab. | Chromium test deliberately holds the initial read, disconnects, releases the response and verifies disconnected UI with no synthetic data restored and no credential reused. |
| Heartbeat failure could be overwritten by a concurrent read, and a timer firing during manual read could permanently lose cadence | Frontend engineer; test engineer owns UI/unit and E2E tests | Heartbeat and read results are tracked independently; never overlap renewal and user read. If the 5-minute timer fires during a read, retain/reschedule cadence; if that read fails, cadence still remains scheduled. Recovery reports `connected` only after heartbeat plus fresh snapshot and events succeed. | Deterministic deferred-promise tests cover heartbeat-failure/read-success completion order, timer firing during read followed by failed read, and full recovery. Assert no duplicate in-flight operations and an active next 5-minute timer where required. |
| JSON control-body regex accepted non-JSON whitespace | Backend engineer; test engineer owns HTTP tests | Accept only JSON syntax for an empty object, including the four JSON whitespace characters outside strings; reject NBSP and other non-JSON whitespace without normalization or trimming. Rejected bodies do not renew or revoke a capability. | HTTP tests exercise JSON whitespace acceptance and NBSP rejection for heartbeat and revoke; after each rejection prove the capability remains usable and state is unchanged. |
| Originless same-origin production read test used a capability bound to a different origin | Test engineer | The capability is paired for the bridge's own origin and the valid same-origin metadata exception is exercised without an `Origin` header. | HTTP test expects a real 200 snapshot response, with the same capability rejected for invalid metadata. |
| Restart invalidation, WebSocket closure, denied metadata matrix, and server-enforced expiry were missing or mocked | Backend and test engineers | Restart creates a new bridge epoch; old capabilities fail. WebSocket upgrade is closed. Pair, control and preflight denied metadata branches fail closed. Expiry is enforced by bridge time/state, not an intercepted synthetic 401. | HTTP restart/upgrade/metadata tests and Chromium expiry test advance the in-process bridge clock past idle expiry and observe the actual 401 path. |
| Pair-body decoding silently removed a UTF-8 BOM before JSON parsing | Backend engineer; test engineer owns HTTP tests | Preserve the BOM in decoded input; strict JSON parsing rejects it and does not consume the one-time code. | HTTP test sends a BOM-prefixed otherwise-valid pair body, expects `400 REQUEST_INVALID`, then pairs successfully with the same unchanged code. |
| Client replaced snapshot `events` before validating required snapshot schema | Frontend engineer; test engineer owns client tests | Validate snapshot response against `SyntheticSnapshotSchema` before composing separately validated events. Missing, null or malformed snapshot events remain an invalid snapshot even when `/events` returns a valid array. | Client tests return valid separate events while snapshot has missing, `null`, and invalid `events`; each yields a recoverable read failure and does not produce connected data. |

The earlier code-review report is a traceability reference, not current-source approval; final code review must be fresh and bound to the completed implementation/checks.

## Non-goals and effect limits

- No OpenCode SDK import, service/client/host start, discovery, connection to existing services, filesystem/Git/process/tool/MCP/PTY action, app data persistence, user project data, credential access, network/registry access, external telemetry, install or package/lockfile change.
- No production bridge static document/assets, native sandbox, OS isolation, same-user process protection, or general local authentication claim.
- Checks may bind only to the pre-approved loopback test ports 5318 (synthetic bridge) and 5420 (Vite UI) and may use the existing synthetic data fixture. Tests must fail if a port is occupied and close owned servers/browser processes on pass/failure. No production `/health` or other unlisted unauthenticated endpoint is added; Playwright starts the bridge in-process after Vite readiness.
- No secrets or real bootstrap code in test output. Any deterministic code exists only as an in-memory fixture constant inside test code.

## Acceptance criteria

- **BSI-1 Admission:** allowlisted loopback reads and exact wire schemas/statuses for endpoint-specific pairing/control flows pass; strict JSON parsing rejects a BOM-prefixed pair body without consuming its code; wrong Host/Origin, bad Fetch Metadata, malformed/duplicate headers, wrong bearer, unknown routes, legacy routes, WS and all domain mutations fail before side effects.
- **BSI-2 Pairing lifecycle:** code is one-use, bounded and memory-only; capability is per-tab, read-only, in-memory, expires/revokes independently, and heartbeat does not grant other authority.
- **BSI-3 UI connection:** the workbench implements each contracted success, recoverable-failure, uncertain-pair, terminal-auth, revoking, and unconfirmed-disconnect state; validates the snapshot's complete wire schema before composing validated finite events; clears the one-time code before submit resolves, uses only direct `credentials: omit` requests, renders the fixture after pairing, and never persistently stores the capability.
- **BSI-4 Browser boundary:** real Chromium E2E proves trusted development-origin `same-site` preflight/pair/read/revoke, actual denied-Origin fetch opacity, server-enforced capability expiry, and target-tab isolation. HTTP tests prove denied metadata branches, bridge-restart capability invalidation, WebSocket closure, strict JSON grammar and originless same-origin read. The test suite asserts unregistered mutation paths return 404 without changing synthetic state; static code review verifies there are no SDK, filesystem, or process-execution call sites in this increment. No runtime effect counters or OS-isolation guarantee are claimed. This evidence is partial relative to parent BB-01..10: it does not satisfy their handler/effect counters or prove every parent scenario.
- **BSI-5 Quality and evidence:** focused HTTP tests plus registered full lint/typecheck/unit/E2E checks pass at the frozen source binding; independent code review has no unresolved high/critical findings and running-app design QA passes or records bounded, non-blocking limitations.
