# Host lifecycle static research — r1

**SSOT:** `docs/runs/build-delivery/plan.md` revision 7; SHA-256 matched packet value `7bcacee7766d65c157a9b1e8b402f9a77e792f6907c89a045b084a62546999d3`.
**Scope:** static reads only. No SDK/client code was executed, imported, instantiated, started or attached. No config/credential files, environment values, network or registry were accessed. No tests were run.

## Finding

A separately isolated probe is feasible to plan, but source inspection does not justify an in-process probe in the coordinator process or a claim that host creation is effect-free. The least-risk target is the documented Promise embedded host, started in a disposable child process with an allowlisted environment, explicit empty configuration, in-memory DB, network denial at the OS boundary, no session/plugin/tool calls, a one-request budget, and a hard timeout plus child-tree cleanup. The probe can then establish startup, one `server.info()` result, and orderly close under those controls. It cannot prove the package has no hidden effects or that later real work is safe.

## Entrypoints and initialization path

- The local spike pins both `@opencode/sdk` and `@opencode/client` to `2.0.18` (`spikes/sdk-ui/package.json:9-14`; lock entries `spikes/sdk-ui/pnpm-lock.yaml:753-800`). `@opencode/sdk` package root resolves to `dist/index.js` (`spikes/sdk-ui/node_modules/@opencode/sdk/package.json:18-34`); that file imports bundled chunks and exports `OpenCode` (`.../dist/index.js:1-8,42-60`). `OpenCode.create` delegates to `PromiseSdk.create` (`.../dist/chunks/opencode-j34yx374.js:8-14`; public types `.../dist/opencode.d.ts:1-7`).
- Promise creation is `create4` in `.../dist/chunks/opencode-kp70gr0x.js:17-45`: it calls `Effect.runPromise(create5(...))`, creates `@opencode/client` with `baseUrl: "http://opencode.local"` and the embedded host's injected `fetch`, registers any supplied plugins, then returns client APIs plus `close`/`Symbol.asyncDispose`. `create5` is `EmbeddedHost.create` in `.../dist/chunks/opencode-b54z5jwe.js:16-52`: it builds `createEmbeddedRoutes`, defaults app name to `sdk` and DB path to `:memory:`, creates a ManagedRuntime, starts `SessionRestart.Service.resumeSuspendedSessions`, builds a Web Request handler, and returns in-memory fetch plus services. Initialization error disposes the runtime (`:51`).
- The SDK README describes the root as an in-process host, explicitly says it opens no listener/network hop, and documents `close()`/async disposal releasing router resources, Location services, fibers and scoped plugin registrations (`.../README.md:1-16,18-29`). This is package documentation; the route implementation corroborates that `EmbeddedHost.create` calls `createEmbeddedRoutes` and does not call the standalone server process (`.../dist/chunks/opencode-b54z5jwe.js:27-42`). The separate `@opencode/server` `ServerProcess.start` does bind a Node HTTP listener (`spikes/sdk-ui/node_modules/.pnpm/@opencode+server@2.0.18.../node_modules/@opencode/server/dist/process.js:86-105,136-152`), but that is not the embedded route entrypoint.
- `createEmbeddedRoutes` eagerly assembles broad service groups, including `Database`, `EventLogger`, `Job`, `Project`, `Worktree`, `Session`, `SdkPlugins`, `PersistentPty`, `Credential`, `Mcp`, `InstructionDiscovery`, `Watcher`, `Workspace`, and an outbound `httpClient` (`.../@opencode/server/dist/chunks/service-status-74x861p1.js:38-100`). Its standard replacements apply DB, PTY, event, app/model, watcher, filesystem-search, global/config, instruction-discovery, shell-selection and MCP settings (`:102-149`). This is a wide capability surface even when the probe intends only metadata.
- The distinct client-only public entrypoint is `@opencode/client` root / `./promise`, resolving to `dist/promise/index.js` (`spikes/sdk-ui/node_modules/@opencode/client/package.json:18-25`). `OpenCode.make({baseUrl, fetch})` in the existing synthetic probe is the client constructor (`spikes/sdk-ui/client-probe.mjs:2-16`). Avoid importing `@opencode/client/service`: that subpath is effectful. Its `discover`, `ensure`, and `stop` read a service-registration file under `$XDG_STATE_HOME` or `~/.local/state/opencode/service.json`, issue `fetch` to the registered endpoint, default-spawn `opencode serve --service`, signal PIDs and remove the registration file (`.../@opencode/client/dist/promise/service.js:25-57,120-161,207-255`). The current SDK spike instead uses injected synthetic transport for client tests (`spikes/sdk-ui/client-probe.mjs:7-20,29-35`); its runtime-info probe is also synthetic (`spikes/sdk-ui/runtime-info-probe.ts:8-10,129-160`).

## Effects visible in source

**Filesystem/config.** At embedded runtime acquisition, `Global.acquire` creates directories recursively for data, config, state, log, bin, repos and tmp, then canonicalizes tmp (`spikes/sdk-ui/node_modules/.pnpm/@opencode+util@2.0.18.../node_modules/@opencode/util/dist/global.js:11-24,45-53`). Default roots derive from `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `os.homedir()` and `os.tmpdir()` (`.../dist/global-roots.js:1-16`). `Global.layer` also reads `OPENCODE_CONFIG_DIR` (`.../dist/global.js:51`). Thus a default embedded host can create directories under normal user roots; setting only `options.config.directory` is insufficient to isolate all of them because it changes just the config root passed into Global. SDK `create5` defaults database to `:memory:` (`sdk/.../opencode-b54z5jwe.js:33-37`); DB layer maps that to in-memory SQLite (`core/.../chunks/config-yds56wag.js:35-49,59-80`). Explicit `database.path: ":memory:"` should remain set. Node package conditions select a no-op V1 migration module (`core/package.json:78-84`), but the host still assembles `V1Migration.layer` (`server/.../chunks/service-status-74x861p1.js:145-150`).

**Process/native/socket.** Embedded host source itself does not call `listen`, `spawn`, or `exec`; the standalone server path does bind sockets, but is separate as noted above. `PersistentPty` can spawn detached `opencode-pty daemon`, inherit the process environment, create/read its `service.json`, and use a local owner socket (`core/.../chunks/config-sk3qaz4a.js:97-105,127-175`; registration socket handling `:280-304`). This path is exposed by the assembled API and should not be exercised. Ordinary PTY operations use the native `@lydell/node-pty` binding selected by `#pty` (`core/package.json:42-46`; `core/.../pty/pty.node.js:1-27`). Static package files show it is a native boundary; whether this binding is loaded during root import or only the relevant service path is not proven from the package’s bundled import graph. The client service helper can also spawn, signal and kill a standalone host (`client/.../promise/service.js:49-56,213-255`).

**Network/effect-capable features.** Embedded routing includes an `httpClient`, MCP, credentials, plugins, model/provider services, shell, workspace, process/PTY and filesystem services (`server/.../chunks/service-status-74x861p1.js:38-100,108-149`; SDK dependency list `sdk/package.json:42-50`). The in-memory host has no inbound listener by documented design, but API operations and plugins can perform outbound requests or local actions. The server routes use request handlers for those service APIs; static initialization alone does not show every effect is triggered at startup. `resumeSuspendedSessions` is started at host construction (`sdk/.../chunks/opencode-b54z5jwe.js:38-41`), so a probe must begin with fresh isolated state and must not infer that “no explicit prompt” means no recovery work.

**Environment.** No required secret variable is identified by the public `OpenCode.create` signature (`sdk/.../internal/host.d.ts:13-21`; Promise API `sdk/.../promise.d.ts:6-26`). But transitive package source consults global-root variables and `OPENCODE_CONFIG_DIR`/`OPENCODE_TEST_HOME`; persistent PTY consults `OPENCODE_PTY_BIN` and inherits `process.env`; provider, shell, telemetry, and native-loader code reads environment variables (examples in `core/.../chunks/config-sk3qaz4a.js:97-151`, `util/.../global.js:13-24,45-53`, `util/.../observability.js:17-18`, `core/.../pty/pty.node.js:2-6`). This was static name inspection only; values were not read. The provider-variable set is broad and not exhaustively enumerated here. A child with a minimal allowlist is necessary to prevent ambient credentials/config from becoming capabilities; do not mutate the parent process environment as a substitute.

**Cleanup.** `OpenCode.close()` and async disposal are documented to release scoped host resources (`sdk/README.md:29`); transport close rejects new calls, aborts active requests, waits for tracked requests, then awaits runtime disposal (`sdk/.../chunks/opencode-wyq33nd6.js:11-47`). Initialization failure calls `runtime.disposeEffect` (`sdk/.../chunks/opencode-b54z5jwe.js:51`). These mechanisms do not establish cleanup of the Global-created directories, arbitrary plugin side effects, detached child processes, or effects outside the runtime scope. The PTY daemon uses `detached: true` and `unref()` (`core/.../chunks/config-sk3qaz4a.js:144-159`), so host close alone should not be treated as process-tree cleanup if PTY startup occurs.

## Probe effect manifest and controls (planning recommendation)

Allow only these effects for the first real lifecycle probe: create one unique temporary root; create the SDK's required subdirectories under it; initialize an in-memory DB; instantiate the embedded router; make at most one `server.info()` request through the SDK's in-memory fetch; record only a minimal redacted outcome; call `close`; remove the root after child exit. Do not call session, permission, tool, shell, MCP, provider, workspace, PTY, plugin registration, event-stream, browser or service-discovery APIs.

Required controls: run in a dedicated child process with a clean allowlisted environment (all XDG roots, HOME, TMPDIR and `OPENCODE_CONFIG_DIR` beneath the owned temporary root; exclude provider credentials, tokens and all ambient telemetry/config overrides; control PATH); pass explicit `database.path: ":memory:"`, `config.directory` and `config.file` under that root, `config.project: false`, empty `config.content`, `events.persist: false`, `fs.filewatcher: false`, and no plugins/instances; ensure no user workspace/session state can be selected; deny network egress at OS/process sandbox level; assert no listener and no child process, while monitoring filesystem writes and process/socket creation; enforce an overall deadline and kill/wait the owned child process tree on timeout; always `close` in `finally` and remove only the exact owned root. Application fetch sentinels alone do not block hidden transports. If the needed OS-level network/process/filesystem containment cannot be demonstrated, keep the exercise at static/synthetic evidence.

Static reading cannot confirm that these options disable every side effect, that all dependencies honor the child environment, or that native loading stays inert. In particular, bundled transitive modules and `resumeSuspendedSessions` need targeted dynamic observation inside the isolation boundary before increasing capability. Use synthetic empty config and no existing database; do not point at normal user paths.

## Feasibility, approvals, and next handoff

The plan already asks for a separate reviewed lifecycle plan with exact packages/resources, owned temporary roots, environment/config discovery, process-tree ownership, socket/effect limits, timeouts and cleanup (`docs/runs/build-delivery/plan.md:53-54`). This research supports drafting that plan now. It does not authorize executing the host. Before a real probe, the coordinator should register the exact effect manifest, child-process/OS sandbox mechanism, allowed output, timeout, cleanup procedure, and platform-specific limits in that plan, then obtain the user approval required by the plan for any uncovered privileged boundary. User choices still needed for a later non-probe runtime include supported OS/runtime matrix and persistent data location/retention (plan `:119-124`); neither is needed to justify this disposable in-memory probe. Keep the current AC-8 rule that synthetic observation proves no S-01 lifecycle, S-08 security, S-09 recovery or product readiness (`docs/engineering/runtime-info-boundary.md:36-43`).

## Evidence and limitations

Read-only commands used: `cat`, `sed`, `nl -ba`, `ls -ld`/`ls -la`, `rg --files`, `rg -n`, and `shasum -a 256` on the plan; all inspected source was package text or project source. Package code was never executed. SDK/client/server/util/core runtime evidence is the locally installed pinned `2.0.18` distribution under `spikes/sdk-ui/node_modules`; it may differ from upstream source or another runtime/platform build. Bundled output has chunk names rather than source filenames, so cited paths and symbols are the installed artifact evidence. The exact transitive module activation order, platform-specific package conditions, startup behavior beyond explicit Effect composition, and complete filesystem/network/process effects remain unverified until a separately authorized isolated probe.
