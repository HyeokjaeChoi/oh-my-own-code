## Confirmed requirements and decisions

- Preserve approved product behavior as recorded in PRD v0.6, including its 18 acceptance groups; use OpenCode v2 as the single execution engine and assistant-ui with Tool UI together. Do not add vendor-specific authentication, brand features, public telemetry, cloud services, subscriptions, or an unapproved release destination.
- Deliver the selected Electron app with a trusted main-process local service, app-owned OpenCode `serve` child, and sandboxed renderer; a browser URL alone does not satisfy the requested app. Keep the React/Vite renderer, contracts/UI packages, FSD boundaries, authoritative local-service projection, and selected state ownership. Reuse existing Node bridge logic as main-process service modules where appropriate; do not make a loopback bridge a second desktop authority.
- **Electron is the user-selected shell**, and macOS + Windows are confirmed targets. Electron main owns the app window and exact app-launched OpenCode `serve` sidecar; renderer/preview remain outside host and server credential authority. Desktop-specific contracts and implementation sequence are in the active `desktop-app-bootstrap` run. Fresh current reviews and exact-document-set approval are complete for the bounded Electron bootstrap increment; full-product work remains governed by its separate gates.
- Build for personal local use only; no App Store, public distribution, signing/notarization, auto-update service, paid account, or public telemetry is authorized by this request. Do not infer Windows runtime evidence from macOS builds.
- Preserve the ChatGPT-inspired foundation and existing component/token contracts. Production UI must be inspected in the implemented desktop app; browser and Figma evidence alone are not desktop QA.
- Preserve local-first privacy, explicit permission admission, workspace path boundaries, idempotency/recovery and honest `unknown` states. No hidden network telemetry. Use synthetic fixtures for adversarial and failure testing.
- Start with architecture/spec review, then a smallest real vertical slice. Probe actual SDK/UI package peers and lifecycle before choosing exact versions. Update and re-review this plan if evidence requires a material change.

## Completed historical increment — bridge-owned runtime-info boundary (AC-8)

Revision 5 completed the pinned `@opencode/client@2.0.18` synthetic transport and public-type probe. It established that the SDK returns valid JSON with an incomplete `ServerInfo` shape unchanged, so static declarations do not validate runtime responses. Revision 6 added a pure bridge-owned validator and one-read observation wrapper, then passed the pinned client's injected synthetic response through that exact implementation. This section and its restrictions are historical evidence for AC-8, not the active desktop increment.

The validator receives `unknown`, checks the documented required public fields and nested primitives with bounded admission limits, and emits a newly constructed minimal result. It drops PID, URLs, paths, unknown fields, raw payloads, SDK errors, response text, and credentials from UI and diagnostics. Fixed outcomes distinguish invalid schema from read failure; neither means the host is running, compatible, authenticated, or available. Version shape and runtime compatibility remain separate. The wrapper accepts one explicitly injected `() => Promise<unknown>`, performs at most one read, and has no retry, default fetch, client creation, discovery, startup, subscription, logging, persistence, or browser endpoint.

For AC-8 only, production bridge code has no SDK import; the SDK spike imports the same pure bridge source only for synthetic verification. The historical AC-8 implementation/probe must not start SDK/ambient services, access user configuration or project files, make external or live-service requests, create sessions, answer permissions, call tools/RPC, or persist user data. The synthetic probe is not OS network isolation and grants no actual-runtime authority. The former AC-8 instruction not to change dependencies, lockfiles, or workspace topology applied only to that increment and does not constrain the desktop shell.

The design boundary and exact AC-8 paths/checks remain registered in the run history. Do not reopen or broaden this completed slice while building the desktop shell; any future live SDK host work requires the separate reviewed lifecycle/isolation plan. The AC-8 synthetic evidence remains partial and does not satisfy AC-9 or desktop release readiness.

- **AC-1 Spec readiness:** exact source documents and approvals are registered; independent plan and design-spec reviews pass; product/design handoffs are current before dependent implementation.
- **AC-2 Architecture and runtime:** workspace graph, FSD rules, public exports, desktop shell/renderer/bridge/preview separation, state ownership, compatibility decisions and required SDK/UI probes have reproducible evidence; failed or unverified capabilities remain blocked.
- **AC-3 Product behavior:** PRD AC-01–18 and the seven integrated user scenarios work against the verified runtime contract, with explicit failure/recovery behavior and no unsupported success claims.
- **AC-4 Quality and safety:** applicable unit/integration/desktop-E2E, boundary-negative, synthetic security/failure, privacy, keyboard/responsive/accessibility and lifecycle checks have actual commands, exit results and review evidence; no critical or high unresolved findings.
- **AC-5 Build:** a clean locked install and deterministic production Electron desktop package succeeds on both macOS and Windows, with each build executed on its target OS; renderer bundles exclude main-only code and secrets; app/sidecar hashes, source revision, runtime/toolchain and launch instructions are recorded. Public distribution, signing/notarization and update service are separate scope.
- **AC-6 Local monitoring:** redacted local health/event/diagnostic surfaces, recovery steps, backup/migration/rollback evidence and personal-use metric definitions are implemented and exercised with synthetic incidents inside the desktop app; no external telemetry is sent.
- **AC-7 Client probe:** the pinned OpenCode client public types and synthetic request/transport/HTTP/JSON outcomes are checked without network access or user data. This is partial AC-2 evidence only and does not establish a real service, S-01 host lifecycle, S-08 security, S-09 recovery, or full product readiness.
- **AC-8 Runtime-info boundary:** the bridge validates unknown runtime-info values, invokes one explicitly injected read at most once, emits minimal normalized metadata or a fixed redacted failure, and never autostarts, retries, logs raw data, persists, or exposes an SDK endpoint. Synthetic client evidence is partial only and does not establish host health, compatibility, authentication, S-01 lifecycle, S-08 security, S-09 recovery, or product readiness.
- **AC-9 Desktop runtime:** the installed Electron app owns its window and exact app-launched OpenCode v2 `serve` sidecar through the trusted main process and typed/narrow preload API. Renderer code has no general Node, shell, filesystem, child-process or sidecar credential access; untrusted preview receives no preload capability. Packaged lifecycle and exact child-reaping evidence passes independently on macOS and Windows.

## Stop, diagnosis and retry policy

When a check returns `NO-RUN`, a required capability/access is unavailable, or two correction cycles fail to advance the same outcome, stop the affected path and record exactly one primary cause: **requirement uncertainty**, **wrong approach**, **implementation defect**, or **tool/access failure**. Record the supporting evidence, affected phase, and a corrective action that changes the blocking condition. Keep dependent work held until that action is completed and its relevant gate is re-reviewed. Do not respond to a missing capability solely by raising model effort or repeating the same command. This policy does not add approval for already-authorized reversible corrections.
