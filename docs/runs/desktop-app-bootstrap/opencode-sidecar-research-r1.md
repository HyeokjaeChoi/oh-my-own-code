# OpenCode sidecar and browser-loopback boundary research — revision 1

Checked: 2026-09-28. Read-only repository and installed-package inspection. No SDK import/call, server launch, package install, test run, credential/config read, or application change occurred. This is code evidence and implementation guidance, not a runtime compatibility or security result.

## Finding

The existing loopback work validates the browser-to-synthetic-bridge security contract. It was appropriate for the browser prototype, whose renderer directly fetches a loopback HTTP server and pairs with a one-time code. It does not validate an installed app owning an OpenCode process. The current desktop bootstrap plan already says to skip browser pairing in desktop mode and use named preload operations, but that increment still supervises only a **synthetic** bridge. It explicitly defers starting the OpenCode SDK. The user's app-owned OpenCode sidecar requirement therefore belongs in a later, separately reviewed runtime increment; it is not satisfied by the browser tests or the synthetic desktop bootstrap.

## Repository facts

- `apps/local-bridge/src/server.ts` creates the current synthetic server, issues/consumes in-memory pairing capabilities, serves only the fixture snapshot/events and binds its CLI launcher to `127.0.0.1` (default port 4318). It requires an interactive terminal to issue a code. `browser-admission.ts` requires a loopback peer/address and exact `Host`, then applies browser `Origin` and Fetch Metadata rules.
- `apps/workbench-web/src/shared/api/read-synthetic-fixture.ts` makes direct browser `fetch` calls to the bridge, carries the capability as a bearer header, and implements pair/read/heartbeat/revoke. `WorkbenchPage.tsx` owns pairing, capability memory, timers and browser-specific connection states. The existing page is consequently coupled to the browser transport flow.
- The browser tests exercise their intended boundary: Chromium direct preflight/pair/read/revoke, readable trusted-origin application errors versus opaque denied-origin fetch errors, expiry, same-tab capability behavior and inert preview. HTTP tests cover exact Host/Origin/Fetch Metadata admission, capability expiry/revocation/restart invalidation, malformed inputs and WebSocket rejection. Their run plan states that this is partial browser-boundary evidence and makes no OS-isolation claim. These checks do not exercise an Electron main process, preload IPC, an app-owned OpenCode child, or child reaping.
- `docs/workplans/desktop-app-bootstrap/plan.md` revision 3 calls for Electron main → owned utility worker → named typed preload → desktop adapter, `readSyntheticSnapshot()` and `onBridgeStatus()`, no desktop pairing/bearer credential, and retained browser regression coverage. It currently calls the worker's payload a fixed synthetic fixture and says “no live SDK.” Its packaged checks target IPC sender/frame/payload validation, navigation/popups, renderer privilege absence, preview isolation and actual child exit/reap. This is a shell milestone only.
- `docs/decisions/0002-desktop-runtime.md` says browser HTTP pairing/CORS is not Electron security proof and assigns lifecycle to Electron main plus a managed utility process. `docs/engineering/workbench-architecture.md` describes the app bridge as the sole authority and identifies the new `@opencode/sdk` embedded host as a candidate; it contrasts `@opencode/client` service connection as the alternative whose external-process lifecycle must be compared.

## Installed OpenCode v2 package facts

The existing `spikes/sdk-ui/node_modules` contains `@opencode/sdk` and `@opencode/client` version **2.0.18**. This is evidence about the installed feasibility spike only, not the root workspace's dependency set or a selected production pin.

- The installed `@opencode/sdk` README and declaration files describe an in-process host: it serves the assembled server router in memory, opens no listener, exposes session/event/client operations, and has `close()` / async disposal for resources. The root export provides `OpenCode.create()` and its public types. Thus an app-owned Node utility process can own an embedded host, but this is not a separate OpenCode HTTP server process.
- The installed `@opencode/client` types expose `Service.discover`, `Service.ensure`, `Service.stop`, and `Service.headers`. The type comments say `discover` finds a healthy compatible service without starting it; `ensure` ensures one is running and defaults to `opencode serve --service`; `stop` stops the registered local service. `EnsureOptions` allows a command/arguments, extra environment entries, version requirement and `onStart`, but its public return is only an `Endpoint` (URL and optional Basic auth), not an owned child-process handle or exit/reap receipt. Its type comment says environment entries are added to the inherited service environment.
- The client types therefore document useful local-service controls, but alone they do not demonstrate exact Electron spawn ownership, prevention of reuse of a separately launched service, sanitized environment inheritance, packaged executable resolution, exact-process shutdown, or observed reaping. This conclusion about the ownership gap is an inference from the declared API surface; implementation behavior was not inspected or executed.
- The installed client returns service auth data in the endpoint/header API. Keep any service credential in the trusted main/utility boundary; never expose it to the renderer or preload API.

## What the browser loopback evidence does and does not establish

| Existing evidence | It establishes within the browser fixture | It does not establish for an app-owned OpenCode sidecar |
| --- | --- | --- |
| `apps/local-bridge/src/http.test.ts`; `apps/workbench-web/e2e/synthetic-workbench.spec.ts` | Browser-origin, Host, capability, CORS, request-shape and browser UI behavior for the synthetic HTTP bridge | App ownership of an OpenCode executable/host, Electron sender/frame validation, typed IPC schema, utility-process supervision, OS-level isolation, packaged paths/environment, or cleanup after app/child failure |
| Existing browser reconnect/expiry/heartbeat behavior | How a browser tab reports/retries a local bridge connection and how its in-memory capability expires | OpenCode session/event recovery, native child survival/termination, service authentication, or reliable event replay |
| `docs/operations/synthetic-bridge-drills.md` | Bounded synthetic loopback loss/effect/recovery fixtures | UI reconnect, host/SDK reconciliation, durable journal/real effects, or OS background lifecycle |
| Desktop plan's proposed packaged E2E | What should be checked for the **synthetic** Electron worker | It does not become proof for a live OpenCode host merely because it launches a packaged app; the OpenCode process/adapter path needs explicit additional coverage |

Why loopback was tested: the bridge contract being implemented was expressly a browser HTTP pairing contract, and its threat surface includes hostile browser origins, DNS-rebinding Host headers, CORS/Fetch Metadata, iframe/preview requests, and tab-scoped bearer handling. Those checks remain useful for preserving the browser build. They were the wrong evidence to use for desktop process ownership; the current ADR and bootstrap plan correctly separate those boundaries. If the earlier tests were presented as proof that OpenCode itself is safely supervised by the app, that would exceed their evidence.

## Smallest safe sidecar and client paths

These paths are implementation inferences to take through the existing architecture/design gates before changing the plan. They do not grant runtime-operation approval.

1. **One app-owned Node utility process hosting the embedded v2 SDK (smallest boundary).** Electron main starts one packaged utility worker and retains its exact process handle. Inside that worker, create one pinned `@opencode/sdk` host at startup; keep the existing app bridge policy/authorization/audit adapter in that trusted process and call the host through its in-memory API, with no OpenCode listener or loopback pairing. Main exposes only closed, versioned operations to preload; the renderer gets read/request/status operations and sanitized status/events, never the host, raw SDK client, server credential, arbitrary channel, filesystem, or process handle. Utility owns SDK `close()` and reports close completion; main still waits for the exact child exit and records timeout/crash/restart/reap outcomes. This matches the current “one owned utility process” topology, but replacing its synthetic fixture with the real host expands scope and needs a revised plan, reviewed API/security contract, pinned compatibility evidence and explicit user-data/provider boundaries.
2. **Separate app-owned OpenCode service process plus trusted client (literal HTTP sidecar).** Main starts the exact packaged executable with fixed `serve --service`-style arguments, a reserved/private app registration path, loopback-only bind and sanitized environment; it retains the spawned child handle. Only the trusted utility/bridge uses `@opencode/client` with the resulting URL/auth. Renderer still calls the app's typed preload API, never OpenCode HTTP directly. Shutdown targets the spawn handle and waits for exit; do not treat `Service.stop()` or a reported PID as proof that this app's child exited. The installed service helper types are not sufficient evidence that it can safely enforce this ownership model. This path adds a second child/lifecycle and HTTP/auth/reconnect boundary; select it only if process isolation or CLI/server packaging is a required constraint and verify the exact service launch contract.
3. **Avoid a renderer-to-loopback-OpenCode path.** Reusing browser pairing or passing a service bearer into Electron renderer would reintroduce a browser transport/credential boundary inside a trusted desktop app and bypass the narrow IPC contract. The current desktop plan explicitly rejects this for its synthetic bridge; it should remain rejected for OpenCode.

## Checks required at the OpenCode runtime boundary

Before enabling a live host, add exact-version checks separate from browser regressions:

- **Ownership/startup:** only the app's fixed packaged command/utility can create the host; startup readiness is explicit; duplicate launch cannot silently attach to a user's ambient service; environment and working-directory inputs are allowlisted; any auth/bootstrap material stays inside the trusted process.
- **IPC/API admission:** exact sender origin/frame and closed message schemas at main; renderer can request only app-owned operations; bridge authorization is repeated before SDK effects; malformed, replayed, stale, or unknown operations are denied. For the embedded route, validate utility message schemas; for the HTTP route, separately validate loopback binding, server auth, version compatibility and local endpoint ownership.
- **Lifecycle:** SDK host creation failure, close, utility crash, timeout, app quit/restart, and interrupted operation each yield a visible state. Observe `close()` result and actual utility/service child exit; preserve `unknown` after a dispatched operation if its effect cannot be reconciled; confirm zero owned descendants after shutdown.
- **Client/event behavior:** use an exact pinned client/host pair; validate initial snapshot, live event delivery, slow-consumer/disconnect behavior, event gap indication, resubscription and native-state reconciliation. Existing docs state client subscriptions are live-only without replay or automatic reconnect, so do not mark a trace complete from a dropped stream.
- **Packaging/security:** exercise the packaged app using the exact built artifact; inspect renderer bundle for SDK/server code, Node built-ins, credentials and unsafe APIs; prove the SDK/server remains in the trusted utility/service process; record binary/version/artifact hashes and the OS support tested.
