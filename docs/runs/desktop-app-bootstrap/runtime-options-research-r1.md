# Desktop runtime options research (r1)

Research checked against official documentation on 2026-09-28. Product target: macOS + Windows desktop app; OpenCode v2 is intended to be an app-owned sidecar. “Inference” labels identify architectural judgments rather than documented guarantees.

## OpenCode v2 contract

- `opencode serve` starts the API and web server. The v2 CLI docs describe it as a foreground standalone server suitable for a supervisor; `opencode service` separately manages a shared background server. ([commands](https://opencode.ai/v2/docs/cli/commands/), [web/server modes](https://opencode.ai/v2/docs/cli/web/))
- `@opencode/client` connects to an HTTP server using `OpenCode.make({ baseUrl })`; it also supports authentication headers and event subscriptions. The Node-only `@opencode/client/service` API has `discover`, `ensure`, and `stop`; its documented default starts `opencode serve --service` through the standard registration path. ([client SDK](https://opencode.ai/v2/docs/build/client))
- The v2 install page lists standalone CLI binaries for macOS and Windows architectures, and says Windows package managers are unsupported. **Inference:** an app-owned sidecar needs a pinned, per-platform CLI artifact in its build inputs; do not assume the user has a globally installed `opencode`, or that the JS SDK package itself supplies the server executable. ([v2 installation](https://opencode.ai/v2/docs))
- The docs establish a server/client boundary, not an embedded-server API. They do not require that the server be a child of the desktop app. **Inference:** for a strictly app-owned lifecycle, the shell should directly spawn the foreground `opencode serve` process and connect via the SDK `baseUrl`; using `Service.ensure()` may instead adopt/start a registered shared service. Do not assume the SDK client launches a process, or that an arbitrary child-process strategy is mandated by OpenCode. The server defaults to localhost and the web docs describe password protection; pass/hold auth through the privileged host side rather than expose credentials as renderer constants. ([client SDK](https://opencode.ai/v2/docs/build/client), [web/server modes](https://opencode.ai/v2/docs/cli/web/))

## Shell comparison

| Concern | Electron | Tauri 2 | Neutralinojs (third option) |
|---|---|---|---|
| **Sidecar supervision and IPC** | Main process can start child/utility processes; utility processes support `MessagePort` channels. Bundle OpenCode outside ASAR with `extraResources`. Electron IPC is a separate renderer-to-main bridge; OpenCode SDK HTTP is another connection. ([process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [packaging resources](https://www.electron.build/docs/contents/)) | `externalBin` packages target-triple-specific executables. Shell plugin can spawn a sidecar, stream stdout/stderr, write stdin, and kill its child; the renderer must be granted narrowly scoped shell permissions, or host Rust can own process control. OpenCode SDK still connects over HTTP. ([sidecar](https://v2.tauri.app/develop/sidecar/)) | Extensions are declared as separate processes and communicate using Neutralino’s WebSocket extension protocol; the OS API also exposes spawn, stdin/stdout/stderr, exit, and process enumeration. However, docs explicitly say the framework does not kill extension processes automatically. ([extensions](https://neutralino.js.org/docs/how-to/extensions-overview/), [OS process API](https://neutralino.js.org/docs/api/os/), [release notes](https://neutralino.js.org/docs/release-notes/framework/)) |
| **macOS + Windows packaging/build** | Mature packaging choices; `extraResources` places executable resources outside ASAR. A macOS machine can produce Windows NSIS through the documented Wine/Docker route, with caveats; native dependencies generally need target builds or prebuilds. macOS signing works only on macOS. ([contents](https://www.electron.build/docs/contents/), [multi-platform builds](https://www.electron.build/docs/features/multi-platform-build/)) | macOS desktop dev needs Xcode or Command Line Tools plus Rust; outside-App-Store macOS distribution requires signing and notarization. Windows MSI requires Windows/WiX. Windows NSIS cross-build from macOS is documented but less tested and caveated; the guide requires LLVM tools, an MSVC Rust target, `cargo-xwin`, and an external signing command for signed installers. Sidecar binaries must independently exist for each target triple. ([prerequisites](https://v2.tauri.app/start/prerequisites/), [macOS distribution](https://v2.tauri.app/distribute/), [Windows installer/cross-build](https://v2.tauri.app/distribute/windows-installer/), [sidecar](https://v2.tauri.app/develop/sidecar/)) | `neu build` generates app artifacts for supported OS targets and the docs describe prebuilt framework binaries; the app-owned OpenCode executable remains another platform/architecture-specific asset to ship. Packaging formats include portable ZIP and installers. ([CLI](https://neutralino.js.org/docs/cli/neu-cli/), [distribution](https://neutralino.js.org/docs/distribution/overview/)) |
| **Preview/runtime consistency** | Bundles Chromium, so Chromium engine behavior/version is more consistent across macOS and Windows; OS fonts, input, GPU and native integrations still vary. **Inference from Electron’s bundled Chromium runtime.** | Uses WKWebView on macOS and WebView2 on Windows; WebView2 auto-updates and Tauri does not bundle the webview, so engine versions and some behavior can differ across machines/platforms. ([webview versions](https://v2.tauri.app/reference/webview-versions/)) | Uses the platform’s webview/runtime approach; the official docs position it as a lightweight cross-platform web app shell, so expect OS webview differences. **Inference; this research did not establish a pinned cross-platform browser engine guarantee.** ([introduction](https://neutralino.js.org/docs/)) |
| **Renderer/native security boundary** | Separate main and renderer processes. Context isolation and renderer sandboxing are defaults in current Electron; use a narrow `contextBridge` API, disable Node integration in renderers, and validate IPC senders. Flexibility means more security surface and continuous Electron/Chromium/Node updates. ([security](https://www.electronjs.org/docs/latest/tutorial/security), [context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)) | Webview calls cross an IPC authority; capabilities/permissions specify which windows may call which commands and scopes. This is a strong explicit allowlist boundary, but careless permissions or overly broad sidecar argument validators weaken it. ([runtime authority](https://v2.tauri.app/security/runtime-authority/), [permissions](https://v2.tauri.app/security/permissions/), [sidecar](https://v2.tauri.app/develop/sidecar/)) | Renderer calls native APIs through a local WebSocket server using auth tokens; extensions receive connection details. **Inference:** the small shell surface is attractive, but the extension API and token handling still need a threat review, especially if remote or untrusted content is ever loaded. ([extensions](https://neutralino.js.org/docs/how-to/extensions-overview/)) |
| **Lifecycle / signals** | App has explicit `before-quit` / `will-quit` hooks; child management is ordinary host-process code. **Inference:** register shutdown handlers and terminate/wait for the OpenCode child, including forced exit and OS shutdown paths. ([app lifecycle](https://www.electronjs.org/docs/latest/api/app)) | Child handle supports process termination; app/window lifecycle hooks allow close interception. **Inference:** own the child in Rust and stop it on app exit; window close and app quit are not equivalent when supporting tray/background behavior. ([sidecar](https://v2.tauri.app/develop/sidecar/), [window events](https://v2.tauri.app/reference/javascript/api/namespacewindow/)) | Spawned processes can be explicitly terminated, but extension child processes are not automatically killed. **Inference:** shutdown supervision/orphan recovery would be app code and a notable risk for a long-lived server. ([OS process API](https://neutralino.js.org/docs/api/os/), [release notes](https://neutralino.js.org/docs/release-notes/framework/)) |
| **Solo-maintainer burden (inference)** | Lowest conceptual friction for a TS-first team and broad packaging ecosystem; highest bundled runtime/update footprint and a security/update obligation across Chromium, Node, Electron, dependencies, and sidecar targets. | Smaller shell/runtime footprint and explicit permissions; higher up-front burden from Rust host code, WebView divergence, capability design, and managing a separate sidecar build for each target. Windows cross-build from macOS adds toolchain/CI complexity. | Lowest shell/toolchain weight, but less integrated distribution and extension-process cleanup; app must own sidecar packaging, lifecycle supervision, and a WebSocket bridge. The apparent simplicity shifts work into product code. |

No option is selected here. The comparison supports a later ADR decision; benchmark real packaging, signing, sidecar startup/shutdown, and Windows behavior before treating any inferred maintenance ranking as proven.
