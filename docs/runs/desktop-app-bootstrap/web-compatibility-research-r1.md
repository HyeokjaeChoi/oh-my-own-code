# Electron / OpenCode v2 compatibility research r1

Checked 2026-09-28. Scope: read-only compatibility research for the approved Electron desktop sidecar design (plan r20; exact document-set approval r1, receipt `user-approval-r1.json`; research packet `web-compatibility-packet-r1.json`). Sources are official project documentation, release/package metadata, and the OpenCode repository. No packages were installed and no binaries or services were run. This report establishes published/documented compatibility candidates, not a successful build or runtime test.

## Finding

A maintained candidate baseline is Electron **44.4.4** with stable Electron Forge **7.11.2**, using the repository's Node 22.12+ toolchain and its existing pnpm 11 workflow. Electron's release page showed 44.4.4 as the latest stable release checked; Forge's release list and npm package page showed 7.11.2 as the stable `latest` (Forge 8.0.0-alpha.10 is prerelease). The pairing is suitable for a bounded build probe, not yet validated in this monorepo. Forge's official setup guidance says pnpm users should set `node-linker=hoisted`; this repository's `.npmrc` does not set it. The repo manifest declares pnpm 11.17.0 and Node >=22.12.0, so apply the documented linker setting in the implementation increment if Forge requires it.

For the live OpenCode v2 sidecar/client candidate, current v2 docs name **`@opencode/cli` + `@opencode/client`**, not `@opencode-ai/client`. The official v2 client and CLI documentation agree on the network-client / `opencode serve` architecture. npm metadata reports public `@opencode/client@2.0.18`; the installed read-only spike metadata in this repository likewise identifies `@opencode/client@2.0.18` and `@opencode/sdk@2.0.18`. Pinning CLI and client at 2.0.18 is a plausible exact pair to probe, but package metadata and docs do not prove that this app's launch arguments, process ownership, authentication, readiness, or shutdown behavior work.

The exact **`@opencode-ai/client`** name is a separate issue: official OpenCode v2 docs and current public v2 package metadata use `@opencode/client`. The upstream OpenCode app source on its dev branch declares `@opencode-ai/client` as a local `file:vendor/opencode-ai-client-1.17.13-v2.tgz` dependency, showing that this scoped client can be consumed as a versioned built tarball in that source tree. The public npm page for `@opencode-ai/sdk` shows the older 1.18.x line and dev/beta builds; research did not find a public stable v2 `@opencode-ai/client` release. Treat that as “no public stable v2 artifact found,” not proof that no private, tagged, or otherwise addressable artifact exists. Do not silently substitute either the SDK's embedded host or a differently scoped client: either use the selected `serve` sidecar and the exact package/artifact chosen by the coordinator, or return the naming/artifact decision for plan reconciliation.

The new **`@opencode/sdk`** documentation describes an embedded host which assembles the server router in memory and opens no HTTP listener. It is a different topology from the approved app-owned `opencode serve` sidecar. It must not be treated as evidence for, or substituted into, this sidecar plan.

## Compatibility and packaging implications

- Electron 44 bundles Node.js 24.21.0; that runtime is distinct from the host Node used to run Forge. Forge 7.11.2 is the current stable train; Forge 8 is alpha. The root project minimum Node 22.12.0 is compatible with the contemporary Forge toolchain floor, but the exact lockfile and platform package build remain to be probed.
- Keep the Electron host and network client in trusted main-process code. The approved architecture retains exact child ownership in Electron main. The client docs' `Service.ensure()` can reuse/start a registered service, and `Service.stop()` stops that registered service; those helpers alone do not prove the app spawned, owns, or reaps the exact process. For this design, main should spawn the pinned packaged executable directly, then use the client against only its own endpoint. Keep auth headers/endpoints in main; never pass them through preload to renderer.
- Forge/Packager's `extraResource` stages files directly into macOS `Contents/Resources` or Windows `resources`, addressable via `process.resourcesPath`. Place executable sidecars there (outside ASAR), with platform/architecture-specific paths, executable permission on macOS, pinned hashes, and an explicit working directory/environment. A bundled resource path is a packaging mechanism, not runtime evidence that the binary launches.
- OpenCode's v2 CLI page offers standalone macOS Apple-silicon and Intel binaries plus Windows ARM64 and x64 binaries (also baseline x64). The npm CLI uses postinstall platform selection, while its v2 page explicitly says Windows package managers are unsupported. For a deterministic sidecar, the standalone versioned executable per target is the clearer candidate; inspect provenance, hash and test each native artifact. Electron/Forge can target macOS x64/arm64 and Windows x64/arm64, but Windows behavior still requires a Windows run.
- Forge offers macOS ZIP and DMG makers; the DMG maker runs only on macOS. The Squirrel.Windows maker creates Setup.exe, .nupkg and RELEASES, and requires Windows (or Linux with Mono and Wine). A Forge cross-build is not proof of target OS startup. Keep artifact creation separate from the required native packaged E2E evidence.
- No public release is authorized. Electron's distribution guidance says signing helps avoid OS security checks; without signing/notarization, downloaded macOS artifacts can be blocked or warn under Gatekeeper, and unsigned Windows installers can trigger OS trust warnings. Local personal-use artifacts can still be built for bounded validation, but they do not establish smooth end-user installation or release readiness.

## Electron security defaults relevant to bootstrap

Electron documents `nodeIntegration: false` as the default since v5, `contextIsolation: true` since v12, and renderer sandboxing as the default since v20. Explicitly set all three on every privileged window anyway, keep the preload API narrow and typed, validate IPC sender/frame and payloads, restrict navigation/new windows, define restrictive CSP, and keep preview content in a separate unprivileged webContents. Do not disable `webSecurity`. Defaults are version-specific behavior, not proof that the app's configuration preserves them.

## Probe boundary

Proceed with the approved synthetic workspace/disposable config and exact app-owned binary only. Record the precise CLI/client package names and tarball/binary hashes before runtime checks. Probe one startup/readiness/request/shutdown path before implementing broader UI behavior; then separately record macOS and Windows native package and lifecycle results. Stop for plan reconciliation if only the internal `@opencode-ai/client` tarball is acceptable but no approved, immutable artifact can be identified. Nothing here justifies access to ambient OpenCode service state or user/global credentials/configuration.
