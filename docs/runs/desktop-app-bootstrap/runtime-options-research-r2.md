# Desktop runtime decision evidence — revision 2

Checked: 2026-09-28 against official framework documentation and the current repository shape. Product target: macOS + Windows; app-owned OpenCode v2 `serve`; TypeScript/React/Nx workspace. Documentation establishes APIs and supported mechanisms, not successful packaging or runtime behavior for this application. All effort, burden, and suitability rankings below are explicit architecture inferences.

## Decision-relevant comparison

| Decision factor | Electron | Tauri 2 | Neutralinojs |
|---|---|---|---|
| **Using the OpenCode TypeScript client in a trusted host** | Electron main is Node.js, so the app can keep `@opencode/client`, typed bridge, process supervision and OpenCode auth inside the existing TS runtime. The OpenCode executable remains a separately pinned child process. **Inference:** least new language/runtime surface for this workspace. | Native commands run in a Rust core. A secure design can own `serve` in Rust and use an HTTP client there, or add a separately packaged Node/TS helper for `@opencode/client`. **Inference:** either moves work away from the current TS host or adds a second trusted runtime. | Native operations live in the framework server or extensions over WebSocket. A TS extension/helper can use the OpenCode client, but introduces another process and authenticated local IPC boundary. **Inference:** more lifecycle/auth glue than Electron for this product. |
| **Bundled `serve` executable** | Main process can spawn the exact pinned per-OS binary, retain its child handle, and hold credentials inside the main process. Packaging resources outside ASAR is supported. The application must implement readiness, auth, timeout, restart policy and exact exit/reap evidence. | `externalBin` supports target-triple sidecars. The official JS shell plugin can launch a sidecar with permission grants; for least authority, keep launch in Rust and expose closed application commands rather than granting general shell command power to the renderer. Rust-side lifecycle and exact ownership still require application code. | Framework process APIs and extensions can start processes, but the framework release notes state extension processes are not automatically killed. The application must explicitly supervise `serve`, authenticated WebSocket extension connections, shutdown and reaping. |
| **Renderer/native authority** | Context isolation and renderer sandboxing are default/recommended, but main/preload are privileged. Use no renderer Node integration, a narrow typed `contextBridge`, sender validation, restrictive CSP, navigation/window denial, and separate preview isolation. Electron's flexibility increases the consequences of a bridge mistake. | WebView receives system authority only through IPC commands and configured capabilities/scopes. CSP is available but must be configured. The capability model is explicit; broad commands or permissions can still grant excess authority. | Native APIs are individually permissioned and use a local WebSocket/token model; extensions also receive connection details. Restrict APIs and extension origins, and review token/process exposure. Avoid giving preview or remote content native API access. |
| **Cross-platform visual/runtime consistency** | Chromium is bundled, which makes browser-engine behavior more consistent between macOS and Windows; OS fonts, input methods, accessibility and native integrations still vary. **Inference.** | Uses platform WebViews (WKWebView and WebView2), so rendering/runtime versions can vary by OS and installation. **Inference from official platform runtime docs.** | Also uses platform-native WebView behavior; no pinned common browser engine guarantee was found in reviewed official documentation. **Inference.** |
| **Personal package / build effort** | Familiar TypeScript/Node toolchain and established packaging ecosystem align with existing workspace. It ships a larger runtime and creates a recurring Electron/Chromium/Node update and security workload. Cross-builds do not prove native behavior; Windows runtime evidence still requires Windows. | Smaller shell package is a likely benefit, but not benchmarked here. Rust toolchain and platform dependencies add learning/build work; sidecar assets must match target triples. Windows installer/runtime evidence remains Windows-specific. | Small framework footprint is attractive but packaging alone does not remove the app-owned sidecar/extension lifecycle, authentication, security and repair work. Less integrated supervision may transfer work into product code. |
| **Evidence still required** | Probe packaged `serve` artifacts, trusted main/client transport, security boundaries, shutdown/reap, native macOS package and actual Windows package. Measure artifact size and idle memory before claiming a resource tradeoff. | Same probes, plus Rust-to-client/API boundary, per-target sidecar staging, platform-WebView differences, and actual Windows native build/runtime. | Same probes, plus extension auth/token handling, server/extension startup order, orphan cleanup, update/package behavior, and actual Windows runtime. |

## Recommendation and limits

**Recommend Electron for this repository, but do not select it on the user's behalf.** It aligns with the existing TypeScript/React/Nx system and permits the OpenCode TypeScript client, trusted bridge and sidecar supervision to remain in one Node-capable host. This reduces new runtime and language boundaries for a solo maintainer. The cost is a larger bundled runtime and an ongoing Electron/Chromium/Node security/update obligation; this recommendation does not claim a small bundle, low memory, or better runtime performance.

Tauri 2 is a strong alternative if measurements show Electron's package or memory cost matters enough to justify a Rust host and explicit capability design. Neutralinojs is plausible for simple lightweight shells, but the documented extension cleanup obligation is a poor fit for a long-lived critical `serve` sidecar unless a reviewed supervisor removes that gap. User preference may override the recommendation after reviewing these tradeoffs.

The evidence establishes documented capabilities only. No exact shell/server/client compatibility, native startup, code signing, actual OS security, package size, idle memory, Windows launch, app-owned readiness/authentication or shutdown/reaping was executed. Selection needs explicit user choice; implementation remains blocked until then.
