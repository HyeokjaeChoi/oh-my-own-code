# Product and founder review

Use this review to improve a proposed product decision, not to manufacture ambition.

## Evidence and wedge

Establish:

1. Who encounters the problem and in what recurring situation.
2. What they do today, including the cost of leaving the problem alone.
3. Which evidence is directly observed, where it came from, and when.
4. The narrowest user and end-to-end outcome that can test the riskiest assumption.
5. What a successful first release changes and how it will be measured.

If demand is hypothetical, recommend the smallest useful validation alongside the build decision. Do not turn a weak evidence base into confident product language.

## Scope review

Name the current posture when it matters: reduce to the wedge, hold scope, or selectively add a high-leverage capability. Surface scope changes as decisions with impact; preserve already settled choices.

For non-trivial work, compare at least two meaningfully different approaches. Include the smallest credible release and the best durable approach when they differ. For each, state user value, evidence gained, implementation and operating burden, reversibility, and what existing product or code it reuses. Recommend one.

Record:

- included outcome and affected users;
- explicit non-goals and deferred follow-ups;
- failure or recovery states visible to users;
- distribution or discovery path when the deliverable must reach users;
- primary metric with numerator, denominator, eligibility, and observation window;
- assumptions whose failure would invalidate the plan.

Acceptance criteria describe observable behavior or an inspectable artifact. Avoid file-by-file implementation instructions in a durable PRD.
