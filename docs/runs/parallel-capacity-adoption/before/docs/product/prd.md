**v0.1 · 2026-09-26 · 독립 제품 검토 및 사용자 승인 전**

이 문서는 승인된 [기회 정의 v0.1](opportunity.md)을 제품 동작으로 구체화한 제안이다. 원페이저의 승인 전 표기는 작성 당시 상태이며, 현재 승인 범위는 [승인 기록](../runs/prd/opportunity-approval.json)에 있다. 아래 예제, 판정 방식, 재시도 규칙은 PRD에서 제안한 결정이지 사용자가 이미 상세 지정한 사실이 아니다. 작성 기준은 [실행 계획 revision 1](../runs/prd/plan.md)이다.

## 1. 누구의 어떤 이해를 돕는가

사용자는 본인 한 명이다. 에이전틱 하네스의 agent/model, 지침·skill, tool/MCP, 권한, hook·검증이 맡는 역할과 **설정 → 실행 → 결과**의 연결을 이해하려 한다. 현재 대안은 공식 문서와 OpenCode CLI를 읽고 실행 기록을 직접 대조하는 것이다. 이 방식으로 충분한지, 별도 UI가 이해를 더 돕는지는 아직 측정하지 않았다.

가설은 작은 예제에서 결과를 먼저 예측하고, 실제 근거를 확인한 뒤 설정 하나만 바꿔 비교하면 구성요소 역할과 권한의 영향을 설명하기 쉬워진다는 것이다. 첫 버전의 목표는 기능 수나 대화량이 아니라 두 예제에서 네 가지 질문에 근거를 들어 답하는 능력이다. 수요, 시간 절감, 학습 향상에 대한 관측 결과는 현재 **미측정**이다.

사용 형태는 본인 컴퓨터의 로컬 브라우저다. assistant-ui가 대화, 도구 결과, 질문과 승인 경험을 담당하고, 구성 지도·타임라인·상세 패널이 학습에 필요한 연결을 보여준다. 첫 사용 가능한 버전은 아래 동작과 기술 검증, 개인 학습 평가를 통과한 로컬 버전을 뜻한다.

**초기 범위:** 고정 합성 예제 두 개, 한 번에 활성 세션 하나, 읽기 도구 하나, `ask`/`deny` 비교. 나머지 구성요소는 설명과 확인 가능한 출처 탐색을 제공한다. **제외:** 범용 하네스 편집기, 실제 사용자 프로젝트 자동 수정, 병렬 에이전트 비교, 임의 MCP 연결, 계정·결제·팀·공개 호스팅·마켓플레이스. 원격 서비스 추가나 Figma 작업은 이 PRD 작성에 포함하지 않는다.

## 2. 최소 경험과 고정 예제

사용자는 예제를 고르고 구성·출처를 확인한 뒤 예상 결과를 한 줄 기록한다. `ask` 실행에서 대화와 권한 요청을 보고 이번 요청을 허용하거나 거절한다. 실행 후 타임라인에서 권한 판단과 도구 결과를 찾아 설명한다. 이어 권한만 `deny`로 바꾼 새 실행을 비교한다. 이전 대화를 복사하지 않으며, 두 실행을 동시에 진행하지 않는다.

| 예제 | 합성 자료와 고정 요청 | 도구가 반환할 기준 자료 |
| --- | --- | --- |
| EX-01 값 읽기 | `color.txt`의 내용은 `blue`. 요청: “예제 읽기 도구로 color.txt를 읽고 적힌 색을 답하라.” | 문자열 `blue` |
| EX-02 읽고 세기 | `parts.txt`는 세 줄 `red`, `blue`, `red`. 요청: “예제 읽기 도구로 parts.txt를 읽고 red인 줄 수를 답하라.” | 세 줄 원문; 기대 계산 결과는 `2` |

두 예제는 같은 읽기 전용 **‘예제 읽기’ 도구**를 사용한다. 이는 제품상 역할명이며 실제 SDK 도구/API 선택은 기술 검증에서 확정한다. 도구는 이 두 합성 자료만 읽고 파일 변경·셸 실행·네트워크 요청을 수행하지 않아야 한다. 평가 UI의 채점 정답표는 답변 제출 후 공개한다. 구성 지도에서는 자료의 식별자·버전·내용 해시를 볼 수 있고 원문은 실제 도구 결과에서 확인한다.

각 예제의 표준 비교는 `ask → 이번 요청 허용` 한 번과 `deny` 한 번이다. 예제 두 개에 총 네 실행이며, 매번 새 세션을 순차 생성한다. 예제·요청·agent·provider/model·지침/skill·도구·자료 버전과 제공되는 생성 옵션을 고정하고 권한만 바꾼다. 세션 ID·시각·실행 ID는 당연히 달라지며 비교 조건에서 분리해 표시한다. 지원되지 않는 생성 옵션이나 난수 고정은 지원되지 않는다고 기록한다.

모델이 도구를 호출하지 않거나 호출을 반복하여 표준 한 요청을 벗어나면 그 실행은 **비교 부적격**이다. `deny`인데 도구 시작이 관측되면 **정책 실패**로 실행·평가를 중단한다. 미호출이나 정책 실패를 성공한 거절로 세지 않는다. 원래 기록을 보존하며 원하는 결과가 나올 때까지 숨겨서 반복하지 않는다. 문장·표현·계산 오류 등의 출력 변동과 권한 효과를 따로 설명한다. 같은 출력은 같은 권한 동작의 증거가 아니며, 다른 출력만으로 권한 효과를 주장하지 않는다.

## 3. 요구사항과 관찰 가능한 수용 기준

아래 ID는 이후 스펙과 검증에서 유지한다. 모든 기준은 앞으로 확인할 목표이며 현재 통과 결과가 아니다.

| 요구사항 | 수용 기준 |
| --- | --- |
| **REQ-01 구성과 출처 이해** | **AC-01:** 구성 지도에서 agent/model, 지침·skill, tool/MCP, 권한, hook·검증의 역할을 읽을 수 있다. 각 항목은 확인한 설정의 출처·버전 또는 확인 불가 이유를 연다. 미사용·미계측 항목을 실행한 것처럼 표시하지 않는다. |
| **REQ-02 예측과 대화** | **AC-02:** 예제와 구성 스냅샷을 확인하고 예측을 기록한 후 실행한다. assistant-ui에서 사용자 요청, 모델 응답, 도구 요청·결과, 질문·승인 상태가 같은 실행으로 연결된다. 실제로 수신하지 않은 질문·이벤트를 만들어 채우지 않는다. |
| **REQ-03 권한 분기** | **AC-03:** `ask`에서는 요청 대상과 입력을 보고 이번 요청 허용 또는 거절을 선택할 수 있고 응답 전 도구 실행이 시작되지 않는다. `deny`에서는 승인 버튼으로 정책을 우회할 수 없고 도구가 실행되지 않는다. 설정된 deny와 실제 거절 관측을 구분하며, 이 두 동작은 후속 런타임 검증으로 확인한다. |
| **REQ-04 흐름 탐색** | **AC-04:** 타임라인 항목을 선택하면 실행·세션·도구 요청 식별자, 이용 가능한 시각, 상태, 입력·출력, 관련 설정을 찾을 수 있다. 출처가 없는 연결은 확인 불가로 표시한다. 대화와 타임라인의 동일 사건이 서로 모순되는 완료 상태를 보이지 않는다. |
| **REQ-05 한 변수 비교** | **AC-05:** 비교 전 두 실행의 고정 조건과 변경 권한을 나란히 확인한다. 다른 실질 조건이 달라지거나 기록이 불완전하면 부적격 이유를 표시한다. 유효한 비교에서 승인 요청·판정·도구 시작·결과의 차이를 근거로 설명할 수 있다. |
| **REQ-06 중단과 복구** | **AC-06:** 아래 상태 규칙에 따라 대기·거절·실패·취소·단절·부분 기록을 구별한다. 연결 복구만으로 실행 완료 또는 기록 완전성을 선언하지 않는다. 중복 승인·중복 제출과 자동 실행 재시도를 하지 않는다. |
| **REQ-07 기록과 데이터 경계** | **AC-07:** 실행 전 외부 모델 전송 범위를 확인할 수 있고, 기록에서 비밀값이 노출되지 않는다. 실행 기록의 로컬 보관 위치와 삭제 결과를 확인할 수 있다. 삭제 범위 밖인 SDK/provider 기록은 별도로 명시한다. |
| **REQ-08 학습 판정** | **AC-08:** 아래 고정 질문·정답표로 예제별 점수, 근거, 소요 시간, 기준 방식과의 차이를 남긴다. 무효 실행과 누락 답변을 성공 표본으로 바꾸지 않는다. 학습 효과를 평가 전부터 달성했다고 표현하지 않는다. |

## 4. 상태, 근거, 반복 규칙

실행 상태와 기록 완전성은 별개다. 실행이 종료된 사실을 재조회했어도 중간 이벤트가 누락되면 **종료됨 · 부분 기록**이다.

| 사용자에게 보이는 상태 | 가능한 행동과 판단 |
| --- | --- |
| 준비 / 실행 중 | 실행 전 전송 범위와 조건을 확인한다. 실행 중 경과 시간과 마지막 수신 시각을 보여준다. 30초간 새 관측이 없으면 지연 안내와 취소 선택지를 제공하되 실패로 단정하지 않는다. |
| 승인 대기 / 질문 대기 | 사용자 입력이 필요함을 명시한다. 승인에서 이번 요청 허용·거절, 질문에서 실제 제공된 항목 응답, 양쪽에서 실행 취소가 가능하다. 승인 범위를 영구 허용으로 확대하지 않는다. |
| 정책 거절 / 사용자 거절 | 어느 주체가 거절했는지 구분한다. 도구 결과를 생성하지 않고 같은 요청을 자동 재시도하지 않는다. 다른 정책 실험은 현재 실행이 끝난 뒤 별도 실행으로 시작한다. |
| 도구 실패 / 실행 오류 | 수신된 오류와 발생 단계를 표시한다. 결과를 정상 답변으로 대신하지 않는다. 오류 전에 남은 근거를 계속 탐색할 수 있다. |
| 취소 요청됨 / 취소 확인됨 | 취소 요청 즉시 성공으로 표시하지 않는다. 런타임 확인 전에는 진행 여부 미확정이다. 확인 불가 시 기록을 부분 상태로 유지한다. |
| 연결 단절 / 상태 확인 중 | 마지막 관측과 누락 가능 구간을 표시한다. 사용자는 연결·상태 조회를 다시 시도할 수 있지만 요청 재전송은 하지 않는다. 살아 있는 승인 요청인지 확인하기 전 응답 버튼을 잠근다. |
| 완료 / 부분 기록 | 완료는 확인된 종료 상태로 표시한다. 전체 구간의 근거를 확인할 수 없으면 부분 기록 표시를 유지하고 권한 비교·학습 채점에서 제외한다. |

타임라인은 **설정 근거**, **런타임 관측**, **설명용 추론**을 명시적으로 구분한다. 설정 근거에는 출처와 수집 시점·버전, 관측에는 원본 이벤트/조회 출처와 연결 ID, 추론에는 근거 링크와 한계를 붙인다. 런타임 시각이 없으면 수신 시각으로 표시하고, 순서가 불명확하면 인과 순서를 단정하지 않는다. 종료 상태 재조회가 누락 구간을 복원했다는 증거가 없으면 빈칸을 채우지 않는다. 모델 내부 사고 전체나 OS 수준 격리를 보여준다는 표현은 금지한다.

재실행은 자동으로 하지 않는다. 이전 실행 종료가 확인된 뒤, 같은 합성 자료·고정 조건에서 새 세션/실행 ID를 만들고 원래 실패 기록을 연결한다. 종료 여부가 계속 불명확하면 실행 기능을 멈추고 조회·기록 탐색만 제공한다. 권한 우회나 조건 변경을 해결책처럼 자동 적용하지 않는다.

## 5. 사전 고정 학습 실험

첫 개인 평가 전에 질문·정답표·조건·기록 양식을 동결한다. 같은 provider/model과 예제 조건을 마련하고, 먼저 **공식 문서 + 기존 OpenCode CLI**, 다음으로 실험실 UI를 사용한다. 각 방식에서 EX-01, EX-02를 각각 `ask` 허용/`deny` 쌍으로 관찰한다. 사전 환경 설정 시간은 따로 기록하고, 예제 시작부터 네 답변 제출까지는 **방식별·예제별 최대 10분**이다. 각 방식에서 제공된 문서와 실행 근거를 찾아볼 수 있다. 중간 채점·정답 피드백은 UI 답변 제출 후 공개한다.

네 질문은 두 예제에 동일하게 적용하며 문항당 1점, 부분 점수는 없다. 답과 지목한 근거가 모두 맞아야 1점이다.

| 문항 | EX-01 기대 답 | EX-02 기대 답 |
| --- | --- | --- |
| **Q1. 작업에서 도구와 모델은 각각 무엇을 했는가?** | 도구가 `color.txt` 원문 `blue`를 반환하고 모델이 색 답변을 구성했다. 도구 결과와 응답을 구별해 지목한다. | 도구가 `parts.txt` 세 줄을 반환하고 모델이 red 줄 수 `2`를 계산한다. 원문과 계산 응답을 구별해 지목한다. 모델이 오답이면 오류로 설명해야 한다. |
| **Q2. 권한이 적용되었다는 근거는 무엇인가?** | `ask`의 요청→사용자 허용→도구 실행/결과와, `deny`의 실제 거절 근거를 지목한다. 완전성이 확인되지 않은 “이벤트 없음”만으로 미실행을 단정하지 않는다. | 같은 판정 기준을 `parts.txt` 요청에 적용한다. |
| **Q3. 승인 대기와 거절 확인 시 다음 행동은 무엇인가?** | 승인 대기에서는 사용자가 이번 요청 허용·거절 또는 취소를 결정한다. 거절 후 같은 요청은 자동 반복하지 않고 종료 확인 뒤 별도 실험을 선택한다. 해당 상태·조작을 지목한다. | 같은 판정 기준을 `parts.txt` 실행에 적용한다. |
| **Q4. ask를 deny로 바꾸면 무엇이 달라져야 하는가?** | 승인 후 읽기 가능에서 정책상 읽기 불가로 바뀐다. 답변 문구의 동일 여부는 보장하지 않는다. 변경된 권한 설정과 비교 실행을 지목한다. | 읽기 허용 여부가 바뀌며 `2`라는 답변의 출현만으로 도구 실행을 입증하지 못한다. 변경 설정과 비교 실행을 지목한다. |

주 지표는 **UI의 각 예제에서 4점 중 3점 이상이며 Q2를 정답 처리했는가**다. 3/4 기준은 승인된 기회 정의를 이어받고, Q2 필수 조건은 근거 없는 성공 판단을 막기 위한 추가 제안이다. 보조 기록은 기준 방식과 UI의 예제별 점수·합계·시간, 오답 이유, 관측 근거, 비교 부적격 이유다. 두 예제 평균으로 한 예제의 실패를 감추지 않는다.

문항 미응답·시간 초과 답변은 0점이다. 연결/기록/호출 조건 때문에 비교가 무효이면 학습 0점으로 섞지 않고 기술상 미측정으로 남긴다. 방식·예제별 쌍은 명시적 재시도 최대 한 번을 허용하되 이전 기록과 이유를 보존한다. 두 번째도 무효이면 평가를 중단하고 원인을 수정한다. CLI에서 같은 신규 v2 조건을 재현할 수 없으면 기준 비교는 미측정이며 다른 SDK 세대로 대체하지 않는다.

중단·수정 판단도 미리 정한다. UI에서 어느 예제든 목표에 못 미치면 설명·근거 연결을 수정한 뒤 재평가하며 기능을 늘리지 않는다. 기준 방식이 이미 두 예제에서 목표를 달성했고 UI 합계 점수가 높아지지 않으며 총 소요 시간도 20% 이상 줄지 않으면, 문서/CLI만 유지하거나 기록 뷰어로 축소하는 결정을 먼저 검토한다. SDK 연결이 별도 개발 과제가 될 경우 아래 최소 능력 검증 실패를 근거로 같은 축소안을 다시 승인받는다. 고정 순서의 단일 사용자 반복 평가에는 연습 효과가 있으므로 점수·시간 차이는 관측 기록일 뿐 UI의 인과 효과나 일반 사용자 효과를 입증하지 않는다.

## 6. 개인정보와 자격 증명

로컬 브라우저는 완전 오프라인을 뜻하지 않는다. 선택한 모델이 원격 provider를 사용하면 고정 요청·시스템 지침·도구 결과와 필요한 설정 일부가 전송될 수 있다. 실행 전에 provider/model과 전송될 합성 자료 범위를 표시한다. 실제 문서·개인 정보·사용자 프로젝트 경로를 예제에 넣지 않고, 새 계정·서비스·예산을 가정하지 않는다.

provider 자격 증명은 브라우저 대화·구성 지도·기록·공유 파일에 넣지 않는다. 기존 사용 가능한 자격 증명의 안전한 로컬 연결 방식은 기술 검증에서 정한다. 외부 분석·자동 업로드·원격 기록 동기화는 초기 범위에 없다. 앱이 관리하는 예측·실행·평가 기록은 로컬에 보관하고 사용자가 실행별 또는 전체 삭제할 수 있게 한다. 삭제는 앱 관리 사본에만 적용되며, SDK와 provider의 별도 보존·삭제 범위는 확인 후 안내한다. 로컬 저장 암호화나 OS 네트워크 차단을 검증 없이 약속하지 않는다.

## 7. 기술 보류와 다음 승인 경계

기준은 **새 OpenCode v2 세대의 `@opencode/sdk` / `@opencode/client`**다. 기존 `@opencode-ai/sdk`의 `/v2` export나 package major와 혼동하지 않는다. [SDK 조사](../research/opencode-sdk-initial.md)와 [assistant-ui 조사](../research/assistant-ui-opencode.md)는 2026-09-26 공식 문서 확인 결과이며 설치·실행 검증 결과가 아니다.

`@assistant-ui/react-opencode` 공식 어댑터는 존재하지만 실험적이며 조사된 사용 패키지는 `@opencode-ai/sdk`다. 새 v2 호환성은 미확인이다. 아래 항목은 PRD 작성의 차단 사유가 아니라 **의존 구현을 시작하기 전 해소할 기술 보류**다.

| 보류 항목 | 이후 검증 및 결정 기준 |
| --- | --- |
| 패키지와 실행 구조 | 새 세대의 실제 배포 버전과 호환 조건을 고정한다. 로컬 host 내장 방식 또는 로컬 service+client 방식을 자격 증명 경계와 종료·조회 능력에 따라 선택한다. 현재 어느 쪽도 확정하지 않는다. |
| 최소 능력 | 빈 새 세션, 한 읽기 도구, ask 허용/사용자 거절, deny, 스트리밍, 질문 표시, 취소 확인, 종료/상태 재조회, 단절·누락 표시를 합성 자료로 확인한다. 실패 항목과 재현 근거를 남긴다. |
| assistant-ui 연결 | 공식 어댑터가 고정한 신규 v2에서 위 동작을 보존하면 채택한다. 호환되지 않으면 assistant-ui의 사용자 정의 상태 연결을 검증한다. 둘 다 범위 내에서 성립하지 않으면 구현을 보류하고 뷰어 축소 또는 범위 변경 승인을 요청한다. SDK 세대를 조용히 되돌리지 않는다. |
| 기록과 비용 | live-only 이벤트의 재생·자동 재연결을 가정하지 않고 복구 가능 범위를 확인한다. 실제 선택된 모델로 호출·취소의 비용 특성과 평가 예상 비용을 산정한다. 비용·개발 기간은 현재 미산정이다. |

현재 단계의 산출물은 이 PRD 초안뿐이다. 순서는 **정확한 버전의 독립 제품 검토 → 사용자 PRD 승인 → 관련 도메인/기술 스펙과 검토·승인 → 의존 구현**이다. 기술 검증의 실행 범위도 해당 후속 계획에서 정한다. Figma와 디자인 시스템 작업은 승인된 설계 단계에서 진행한다. 제품 출시 판단에는 AC-01~08, 기술 보류 해소, 상태/권한 검증과 개인 학습 평가가 필요하며 어느 항목도 이 문서 작성만으로 완료되지 않는다.
