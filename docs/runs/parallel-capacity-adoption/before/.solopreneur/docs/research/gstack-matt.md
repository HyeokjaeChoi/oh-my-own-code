## What the source actually implements

### gstack

gstack is a generated workflow system rather than a small directory of independent prompts. Authored `SKILL.md.tmpl` files and section templates expand a shared preamble and resolver macros into large final skills. [`scripts/gen-skill-docs.ts`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/scripts/gen-skill-docs.ts) performs host-specific generation. Its [`hosts/codex.ts`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/hosts/codex.ts) adapter keeps only `name` and `description` frontmatter, rewrites Claude paths and `CLAUDE.md` to Codex equivalents, generates OpenAI metadata, suppresses the Claude-to-Codex wrapper and cross-model/GBrain resolvers, and installs a runtime sidecar. Hook declarations are not native-portable: the generator extracts their intent and inserts advisory prose for external hosts.

The planning chain is concrete:

- [`office-hours/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/office-hours/SKILL.md.tmpl) separates startup and builder modes, reads repository context, tests demand and the current workaround through six forcing questions, challenges premises, requires at least two approaches including a minimum and an ideal, and writes a design document. Its [`phase-2a-startup-diagnostic.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/office-hours/sections/phase-2a-startup-diagnostic.md.tmpl) supplies the demand, status quo, desperate specificity, narrow wedge, observation, and future-fit questions.
- [`plan-ceo-review/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/plan-ceo-review/SKILL.md.tmpl) makes scope posture explicit: expand, selectively expand, hold, or reduce. Its [`review-sections.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/plan-ceo-review/sections/review-sections.md.tmpl) then audits architecture, named error paths, security, data and interaction edge cases, code quality, tests, performance, observability, rollout, trajectory, and UI. It persists accepted scope, non-scope, failure registries, diagrams, and review status.
- [`plan-eng-review/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/plan-eng-review/SKILL.md.tmpl) first pins the review target, then challenges scope and produces an implementation-oriented review. Its [`review-sections.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/plan-eng-review/sections/review-sections.md.tmpl) covers architecture, code quality, tests, and performance, plus existing leverage, explicit non-scope, failure modes, diagrams, worktree opportunities, and an implementation task list.
- [`autoplan/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/autoplan/SKILL.md.tmpl) composes CEO, conditional design and DX, and engineering reviews sequentially. It writes every auto-decision into the plan and delays real user challenges to one final approval gate. This is evidence that phase ordering and a disk-backed decision trail are the key mechanism; the multiple model voices and large generated preamble are supporting machinery.

The design and QA chain depends on inspected output, not prose claims:

- [`plan-design-review/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/plan-design-review/SKILL.md.tmpl) and its [`review-sections.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/plan-design-review/sections/review-sections.md.tmpl) evaluate information architecture, interaction states, journey and emotional arc, generic-looking output, design-system alignment, responsive/accessibility behavior, and unresolved choices. Scores are accompanied by a description of what better output would look like.
- [`design-consultation/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/design-consultation/SKILL.md.tmpl) researches the product landscape, proposes distinct visual directions, previews them, and writes an explicit `DESIGN.md` token and rationale contract. It distinguishes research, the chosen direction, and exact implementation values.
- [`qa/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/qa/SKILL.md.tmpl) uses a real browser to establish a baseline, captures screenshots and console state, ranks findings, fixes one source issue at a time, re-runs the affected flow, and records before/after evidence. [`qa-only/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/qa-only/SKILL.md.tmpl) keeps the same evidence model while forbidding fixes. [`design-review/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/design-review/SKILL.md.tmpl) applies the same audit/fix/retest loop to visual quality.
- [`browse/SKILL.md.tmpl`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/browse/SKILL.md.tmpl) is coupled to gstack's Playwright/Bun browser and browser-session handling. The reusable idea is an evidence contract: target URL and revision, viewport/device, action and state, expected versus actual result, console/network evidence where relevant, and screenshot paths.

gstack's Claude hooks are substantial runtime behavior. [`setup`](https://github.com/garrytan/gstack/blob/71f6048e8ada25180e61438abc1d98cb151fe9a7/setup) can register question-preference `PreToolUse`, question-log `PostToolUse`, error fallback, timeline `Stop`, and optional pre-push behavior in Claude settings. This setup is consent-aware and backs up settings, but it still manages a second state root, generated files, symlinks, browser binaries, and host-specific settings. Its current hook system is not a source-compatible replacement for this harness's reviewed native `.codex/hooks.json`.

### Matt Pocock skills

Matt's repository is more composable. Most skills are short, editable Markdown with optional references and `agents/openai.yaml` metadata. [`scripts/link-skills.sh`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/scripts/link-skills.sh) is explicitly a maintainer development linker, not an installer; it symlinks promoted skills into both Claude and Agent Skills directories and can remove a conflicting real directory. It must not be used by this harness.

The strongest reusable workflow is spec to executable issue graph:

- [`to-spec/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/to-spec/SKILL.md) synthesizes existing discussion and code context into a problem, user-facing solution, stories, implementation decisions, test seams, and non-scope. It avoids volatile file paths in the durable spec. It currently insists on extensive stories and confirmation of test seams.
- [`to-tickets/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/to-tickets/SKILL.md) splits the spec into context-sized tracer-bullet issues. Every issue delivers a complete, demonstrable path across the needed layers and names its blockers. Wide mechanical changes use expand-migrate-contract sequencing instead of artificial vertical slices. GitHub issues are created in dependency order so links can use real identifiers.
- [`setup-matt-pocock-skills/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/setup-matt-pocock-skills/SKILL.md) configures the issue tracker, labels, and domain-document layout per repository. Solopreneur already owns these choices through `AGENTS.md`, `docs/product`, `docs/specs`, GitHub Issues/Projects, templates, and its managed application tool, so running this setup would create a competing configuration layer.

The implementation loop is deliberately incremental:

- [`implement/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/implement/SKILL.md) asks for regular focused typechecks and test-file runs, one full suite at the end, then a code review and commit.
- [`tdd/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/tdd/SKILL.md) tests public seams and works one vertical tracer at a time: one failing behavioral test, minimum implementation, repeat. It explicitly rejects tests coupled to internals, tautological assertions, and writing an imagined horizontal test suite before implementation.
- [`diagnosing-bugs/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/diagnosing-bugs/SKILL.md) first builds a fast pass/fail loop for the exact reported symptom, reproduces and minimizes, tests ranked falsifiable hypotheses one variable at a time, converts the repro into a regression test at the correct seam, and removes temporary instrumentation.
- [`code-review/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/engineering/code-review/SKILL.md) pins a fixed comparison point, finds the originating spec, and reports repository-standard and spec-compliance reviews as separate axes. It uses two parallel subagents to prevent one axis from hiding the other.
- [`implement-spec/SKILL.md`](https://github.com/mattpocock/skills/blob/3cca18b368ae95cdbdebbff572ccafa662551015/skills/in-progress/implement-spec/SKILL.md) treats blockers as a task graph, gives each ready issue to a worktree, merges completed branches, advances the frontier, and reviews the final branch. It is marked in-progress and assumes a draft PR, multiple agents, worktrees, and commits for every implementation.

## Adaptation decisions

| Source mechanism | Decision for Solopreneur | Harness mapping |
| --- | --- | --- |
| Demand reality, current workaround, narrow wedge, observable success, and at least two viable approaches | Adopt in compact form. These questions prevent polished specs for hypothetical pain. Ask only when missing evidence changes the product decision; otherwise label the assumption and propose the smallest validation. | Strengthen `solo-product-spec`; product-manager and product-research roles supply independent challenge when the planner routes them. |
| Explicit scope posture and non-scope | Adopt. Record current release, later work, and rejected/deferred choices. Do not run gstack's 11-section review for every feature. | Product spec and plan-review artifacts. |
| Sequential product/design/engineering review with a final decision trail | Adopt the dependency order. Use the root planner to route specialists, save their reports under `docs/runs/<run-id>/`, and let the plan reviewer integrate once. Avoid recursive Codex calls from inside a skill. | Planner and plan-reviewer orchestration owned outside this document. |
| PRD/spec to vertical issues with blocking edges | Adopt. Keep product intent in `docs/specs`; create GitHub issues only when requested or already authorized. Size each issue for one fresh agent context and require a verifiable user path. Use expand-migrate-contract only for genuine wide refactors. | Product-spec reference plus the product-manager role's issue-plan output; GitHub Issue templates remain execution records. |
| Fixed-point, separate standards and spec review | Adopt. Infer the merge base when clear; preserve separate headings so implementation quality cannot mask missing requirements. Use parallel reviewers only when the change is large enough to justify coordination. | Enhance the reviewer role and review run artifact. |
| Public-seam, one-slice red/green loop | Adopt selectively. A behavioral or regression seam should be real and high enough to survive refactors. Do not require user confirmation for routine seam choices already implied by acceptance criteria. Do not require TDD for reversible presentation changes. | Engineer and test-engineer roles; targeted checks after each slice and one relevant broad pass at the end. |
| Reproduce, minimize, falsify, fix, re-run exact symptom | Adopt. This is the clearest source mechanism for hard bugs and performance regressions. | Bug-analyst diagnosis artifact handed to engineer; regression evidence in the run report. |
| Landscape research separated from design decisions | Adopt. Capture sources, dated observations, reusable patterns, and constraints; do not copy a competitor's identity. | New `solo-design-research`, feeding `solo-design-system` or a feature design spec. |
| Explicit design contract with exact tokens and rationale | Adopt while using the existing repository token structure and Figma direction. Avoid gstack's proprietary state directory and mandatory `DESIGN.md` schema. | New `solo-design-system`; output in project design docs and `packages/design-tokens` when implemented. |
| Browser QA with screenshots, console evidence, and before/after verification | Adopt the evidence contract. Keep report-only and fix authorization distinct. Use the browser, simulator, or connected design tools already available to Codex instead of installing gstack's Bun/Playwright/Aside stack. | `solo-design-review` for implemented UI review; design-QA role produces an independent report under the run directory. |
| Real product screenshots versus promotional/store composition | Adopt. Product-state evidence must come from a real runnable build or supplied capture; generated artwork can frame or annotate it but cannot prove behavior. | `solo-store-launch` routes keyword/copy work to `solo-aso`; capture/export work stays in store launch. |
| gstack auto-update, GBrain, telemetry, second state root, generated preambles, browser binary, and question-preference hooks | Reject for this harness. They add a runtime and privacy/maintenance surface unrelated to the user's lean repository workflow. | Keep standalone copied skills, managed hashes, explicit project trust, existing advisory Codex Stop hook, and project-native artifacts. |
| Mandatory per-finding user questions, forced clean tree, automatic commits, stashes, reverts, PR creation, or issue publication | Reject as defaults. They conflict with existing authorization, dirty-worktree preservation, and the requirement to finish useful reversible work before asking. | Infer routine choices; surface consequential decisions. Mutate Git or remote state only within the active request. |
| Matt setup docs, `CONTEXT.md`, `.scratch` tracker, triage label state machine | Do not add globally. They duplicate current repository contracts. A product may add them locally if a demonstrated workflow requires them. | Existing `AGENTS.md`, `docs/product`, `docs/specs`, GitHub Issues/Projects, and `.solopreneur` managed docs remain authoritative. |
| Matt's wholesale symlink linker and gstack setup | Reject. Neither preserves the harness's conflict-detection and standalone project-copy guarantees. | Continue using `scripts/solo.py` to apply versioned source files and report conflicts. |

## Concrete implementation target

The adapted harness should remain smaller than either source bundle:

1. `solo-product-spec` becomes the product/CEO entry: establish evidence, current workaround, narrow release, metric, non-scope, and meaningful alternatives; produce or review the repo PRD without silently implementing it.
2. `solo-design-research` produces a cited pattern-and-constraint brief from current primary sources and supplied references. It records what was inspected and which observations are transferable.
3. `solo-design-system` converts an approved product direction and research into an implementable design contract: semantic tokens, typography, layout, component states, platform differences, accessibility, and a decision log. It updates Figma/repository artifacts only when requested and accessible.
4. `solo-design-review` independently inspects an implemented screen or flow at relevant viewports/devices. Its persistent report includes revision/build, target, steps, expected and actual result, screenshot paths, console/runtime findings when available, severity, and verification limits. When fixes are requested, each correction is re-inspected with before/after evidence.
5. `solo-aso` owns store positioning, keyword hypotheses, metadata, native store experiment plans, and dated evidence. It does not generate or claim screenshots.
6. `solo-store-launch` owns real capture selection, storyboard, localization manifest, exact export requirements, and AppLaunchFlow or available asset tooling. It labels mockups and missing captures explicitly and can consume approved `solo-aso` copy.
7. `solo-marketing` turns the approved positioning into an implemented landing page or campaign asset in the existing Next.js stack, with audience, promise, proof, primary action, analytics events, responsive/accessibility checks, and an evidence-backed preview.

Each orchestrated run should write a small handoff report under `docs/runs/<run-id>/` containing the request and acceptance criteria, source artifact pointers, specialist findings, decisions and assumptions, files changed, validation evidence, and remaining blockers. Specialists should pass paths instead of repeating the PRD, screenshots, or research in prompts. This retains gstack's artifact continuity and Matt's context-pointer discipline without adopting their runtime layers.
