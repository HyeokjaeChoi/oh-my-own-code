# oh-my-own-code — 의사결정 원페이저

**v0.1 · 2026-09-26 · 제안 단계 / 사용자 승인 전**

하네스의 **설정 → 실행 → 결과**를 연결해서 보고, 설정 하나를 바꿨을 때 달라지는 동작을 직접 이해하는 개인 학습 도구.

## 목적과 제안

사용자는 나 자신이다. 확정 요구는 에이전틱 하네스 구성요소의 원리와 흐름 이해, OpenCode SDK v2 활용, assistant-ui 사용이다. 저장소는 `~/Projects/oh-my-own-code`다. **작은 실제 예제를 관찰하고 비교하는 실험실**을 추천한다. 이 학습 방식과 로컬 브라우저 형태는 아직 제안이며, 사용자의 추가 답변 또는 이 문서의 명시적 승인으로 확정한다.

현재의 지침 파일과 실행 결과를 함께 읽는 것보다, 설정과 근거 이벤트를 연결하면 이해가 쉬워질 것이라는 가설이다. 학습 효과나 사용 시간 절감은 아직 측정하지 않았다.

| 선택 | 얻는 것 | 부담과 한계 |
| --- | --- | --- |
| 공식 문서 + 기존 OpenCode CLI | 바로 실험 가능한 가장 작은 대안 | 설정과 기록의 연결을 직접 따라가야 한다. |
| 설명·기록 탐색 뷰어 | 구성요소 관계와 과거 흐름을 이해 | 설정 변경의 영향을 직접 실험하는 범위는 작다. |
| **작은 실행 실험실 — 추천** | 같은 예제에서 한 설정을 바꾸고 차이를 관찰 | 실행 상태 연결과 기록 누락 처리가 필요하다. 일반 개발 도구로 범위를 넓히지 않는다. |

## 첫 버전에 담을 경험

**예제 선택 → 구성 확인 → 결과 예측 → 실행·승인 → 타임라인 탐색 → 설정 하나 변경 → 비교**

- **구성 지도:** agent/model, 지침·skill, tool/MCP, 권한, hook·검증의 역할과 관계를 설명한다. 실제 확인된 설정의 출처와 버전을 연결하고, 확인 불가능한 적용 여부는 표시한다.
- **대화와 관찰:** assistant-ui로 대화·도구 결과·질문/승인을 보여준다. 별도 타임라인과 상세 패널에서 세션, 이벤트 시각, 입력·출력, 상태와 연결된 구성요소를 탐색한다.
- **최소 실행 범위:** 합성 예제 작업공간, 세션 하나, 도구 하나, 권한 분기부터 시작한다. 첫 비교는 같은 작업의 도구 권한을 `ask`와 `deny`로 바꾸는 것이다. 나머지 구성요소는 설명/출처 탐색부터 제공하며, 계측되지 않은 hook·검증·MCP 실행을 실제 관측처럼 그리지 않는다.
- **정직한 상태:** 승인 대기, 거절, 도구 실패, 사용자 취소, 연결 단절·기록 누락을 구분한다. 관측 기록과 설명용 추론을 구별하고 모델 내부 사고 전체를 보여준다고 주장하지 않는다. 누락된 기록을 추정해 성공으로 채우지 않는다.

## 기술 선택에서 확인할 것

assistant-ui의 **공식 OpenCode 어댑터는 존재하지만 실험적**이며 `@opencode-ai/sdk`를 사용한다. 신규 `@opencode/sdk`·`@opencode/client`와의 호환성은 아직 검증하지 않았다. 신규 v2를 연구 기준으로 유지하되, PRD에서 SDK 세대를 명확히 하고 기술 검증에서 어댑터 사용 여부를 결정한다. 호환되지 않을 때는 assistant-ui의 사용자 정의 상태 연결 방식을 검토하며, SDK 세대를 조용히 바꾸지 않는다. [어댑터 근거](https://www.assistant-ui.com/docs/runtimes/opencode/overview), [사용자 정의 연결](https://www.assistant-ui.com/docs/runtimes/custom/external-store)

신규 v2 이벤트 스트림은 자동 재연결·이벤트 재생을 보장하지 않는다. 완전한 실행 이력을 주장하기 전에 상태 재조회와 누락 표시를 검증해야 한다. [OpenCode client](https://opencode.ai/v2/docs/build/client/)

## 진행·수정·중단 기준

먼저 두 개의 짧은 예제에서, 각 실행 후 **구성요소 역할 / 권한이 적용된 근거 / 다음 단계 / 설정 변경 후 예상 차이** 네 문항에 답하고 근거를 지목한다. 제안 성공 기준은 **첫 개인 검증 세션의 2개 예제 각각 4문항 중 3문항 이상 정답**이다. 예제별 기대 답과 판정 기준은 검증 전에 정하고, 기존 문서·CLI 방식으로도 같은 질문에 답해 비교한다.

기존 방식만으로 충분하거나 UI를 본 뒤에도 차이를 설명하지 못하면 구현 범위를 축소하거나 설명 방식을 수정한다. SDK 연결 자체가 큰 별도 개발 과제가 되면 초기 뷰어로 축소하는 안을 다시 결정한다. 구현 기간과 호출 비용은 SDK·모델 선택과 짧은 기술 검증 후 산정한다.

첫 배포는 본인 컴퓨터에서 쓰는 버전을 제안한다. 계정·결제·팀 기능, 공개 서비스, 마켓플레이스, 임의 실제 프로젝트 자동 수정, 전체 하네스 편집기, 병렬 에이전트 비교는 초기 범위 밖이다. Figma와 현재 디자인 시스템 선택은 스펙 승인 뒤 진행한다. SDK 연결·권한 거절·취소·기록 누락 검증과 개인 학습 평가를 통과해야 사용 가능한 첫 버전으로 판단한다.

**결정 요청:** 이 실험실 방향과 첫 버전 범위로 PRD를 작성할지 승인한다. 원페이저 승인은 PRD·스펙·앱 구현의 완료를 뜻하지 않는다.
