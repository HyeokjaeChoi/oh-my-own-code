# Development entry route

Use when the user wants full-stack coding or a bounded frontend, backend, mobile, data, or other implementation slice from an existing contract or codebase. Design-only creation of missing resources enters [idea-to-launch.md](idea-to-launch.md) at its relevant approved product/design stage. Do not run idea discovery, market research, a new PRD, or every lifecycle stage by default.

Read the supplied PRD, design resources, repository instructions, code, tests, and open issues. Confirm the project name and exact owned slice, expected behavior, acceptance criteria, target environment, and intended endpoint (plan, verified build, or release). Before coding, make a concise input-readiness record with:

- **Completed PRD:** exact file/link and version, approved scope and acceptance criteria, current user adoption, and required independent product review.
- **Separate design resources:** exact file/link and version, access, current user adoption of that version, and fit to the slice. For frontend/mobile/full-stack, require an existing design system or `design.md` **and** the relevant flow, screen/state, or component contract for the UI being coded; include assets when the accepted design depends on them. A general design system alone does not authorize an unspecified screen or journey. For backend-only work, require a distinct API, data, service, or architecture design contract. PRD prose cannot satisfy this second input by itself.
- **Handoff:** register the PRD for a current `product_reviewer` pass and product `handoff`. Register each required design-resource contract, including a backend API/data/service design at a custom path, with `--type design_spec` and a matching contract document entry; obtain `design_spec_reviewer` pass and design-spec `handoff` before coding from it. For backend-only design resources, review API/schema/security/state/error contracts and consumer compatibility. Technical implementation plans and tasks belong under `docs/engineering/`; product requirements stay under `docs/specs/`. Identify any contradictory, stale, or inaccessible input.

Trace current code with `$solo-evidence-research` and `code_explorer`; ask a narrow question only when a missing decision changes implementation or verification. If the user's current prompt clearly adopts specific current PRD and design versions and authorizes implementation, that is approval; do not demand a duplicate sign-off. If either required input is missing or not ready, report the exact gap and hold dependent coding. Ask the user to supply the existing artifact or extend scope to product/design completion via the relevant route; do not silently draft a replacement PRD or design system under a development-only request. Independent reviewer pass alone does not equal user approval.

Use `$solo-orchestrate` for the plan SSOT and independent plan review. For substantial work, `$solo-engineering-plan` translates the approved contract into owned vertical slices and interfaces. For a bounded slice, use a compact plan. Implement only the selected platforms with `$solo-implement`, reusing the existing stack and design system unless the user asks to change them. If the slice depends on an account-backed design tool or remote design file, apply the tool-choice and authenticated-read hold in [idea-to-launch.md](idea-to-launch.md#3-design-after-spec-approval) before tool-dependent work; independent research may continue. Repository-local design files require direct read/access and the document gates above, not MCP authentication. Add analytics, subscription, release, or monitoring work only when requested or required by the accepted scope.

Select checks according to changed behavior: format/lint/type, meaningful unit/integration coverage, and browser/device E2E for critical affected journeys when available. Use `$solo-qa-run` for observation and `$solo-code-review` for independent code judgment; use `$solo-design-review` for implemented UI with current rendered evidence. A scoped backend task does not need visual QA. Complete the agreed endpoint and report direct evidence, unresolved dependencies, and next decision. Release or production changes follow the user's actual authorization and the `$solo-release` gate.
