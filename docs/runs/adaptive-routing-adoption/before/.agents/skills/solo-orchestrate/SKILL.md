# Product workflow coordinator

Clean-context invariant: every specialist dispatch starts a fresh child context. The primary session remains the sole orchestrator, integrator, and ledger writer; specialists receive the plan SSOT and artifact paths rather than the primary transcript. Corrections start a new clean child with the prior report referenced by path.

Use this at the start of each new task as the primary coordinator, using the current conversation model and reasoning effort. For a factual question or status request, make the scope decision briefly and answer; continue any active work. For work that changes artifacts or prepares execution, use the run protocol below. A follow-up to the same outcome normally resumes its run.

Read the relevant product facts, acceptance criteria, existing answers, and run record. Ask focused follow-up questions until execution-relevant requirements are clear. Hold dependent implementation while blocking questions remain; continue independent discovery. Record user-delegated choices and supported assumptions; silence is not confirmation. Do not re-ask settled questions or create another approval step for authorized work. Translate the outcome into narrow scope, observable completion criteria, evidence, and the smallest useful sequence of assignments. Assign roles by needed judgment and evidence, not model tier.

For substantive feature work, iterative design, or repeated failures, use [effort-and-feedback.md](references/effort-and-feedback.md): clarify the written spec, deliver a bounded increment, inspect intent with feedback, and verify the affected risks independently. Separate implementation speed from verification completeness. Select a feedback point that can change a decision; do not add approval pauses or specialist calls to every edit. Its effort examples are calibration advice, not permission to change inherited settings.

For artifact work, read [planning-contract.md](references/planning-contract.md). Persist the confirmed task plan at `docs/runs/<run-id>/plan.md` as the SSOT, with revision, requirements, decisions, open questions, assignments, checks, and change history. New user direction takes precedence: update and independently re-review changed concerns before dependent execution. Link durable product/design/engineering contracts without creating competing execution plans.

For project work, use `python3 .solopreneur/harness.py`; in the toolkit source use `python3 scripts/harness.py`. Read [run-protocol.md](references/run-protocol.md) for schema v2 contracts, exact check commands, review bindings, prepared handoffs, outcome coverage, recovery, and migration. Select the task kind and declared document/UI gates to match the actual work.

Before implementation, request an independent `plan_reviewer` in a fresh child inheriting the current conversation settings. Give it the user outcome, current evidence, constraints, proposed plan, and open choices. Resolve material findings and record the reviewed plan. This is peer review, not a new user approval requirement. Research may precede it; artifact implementation follows it. A typo- or label-only change may use a compact plan and review; see run-protocol.md.

Dispatch only needed roles with the current plan path and revision/hash, bounded outcome, input paths, owned files, acceptance criteria, and report path under `docs/runs/<run-id>`. Route `code_explorer` and `web_researcher` to factual retrieval; send recommendations, architecture choices, and other judgment to the appropriate judgment role. Use `qa_runner` for specified observation-only checklists and browser/device evidence, then send its report to `design_qa`, `reviewer`, or another required final reviewer; `qa_runner` cannot issue or satisfy a final gate. Keep dependencies ordered; cap parallel specialists at three. After a capacity failure, reconcile live task state and completed outputs before retrying with backoff, and diagnose host capability or transport first; a transport stall is not evidence for changing models or effort. Omit model and effort on an ordinary spawn. Pass only an explicit user-requested supported override; report an unsupported choice rather than substituting another. Before assigning implementation that consumes product/design documents, register them, obtain independent `product_reviewer`/`design_spec_reviewer` passes, and run the matching `handoff` check. Document changes require renewed review. Read-only reviewers return reports for the coordinator to persist; authors do not approve their own independent review. Compatible independent judgments may share one bounded handoff only when each verdict remains separately identified.

Every feature or bugfix needs an independent code gate regardless of size; scale depth to risk. Final reviewers return fixes to implementers and cannot approve their own repairs.

Use the product cycle as routing, not a requirement to build every platform or release every change: idea → brief/PRD → design exploration/system → engineering plan → implementation → tests → code/design/product review → instrumentation → authorized release → reliability/analytics → next experiment. For a bounded request, stop when its requested outcome is complete and record the next owner; continue the entire cycle when requested.

Complete affected checks and reviews against current inputs. Verify capture paths, viewport/device dimensions, and direct evidence before dispatching a visual reviewer; do not rely on inherited history or an old screenshot. Freeze artifact registration and selected checks before final review, then rerun all recorded checks after a source fingerprint change; retain passing checks when only run reports change. Do not create a perpetual test loop. Resolve failed/stale evidence instead of editing the ledger to manufacture success. A successful ledger check verifies record consistency, not product correctness or reviewer identity. Record inherited or explicitly requested routing separately from actual runtime observation; neither role files nor coordinator metadata prove runtime identity. Release execution and final release judgment require separate assignments, with a fresh independent `release_engineer` review. Report concrete outcomes, evidence, and remaining external dependencies. Existing authorization governs external mutations; finish the reviewable local result before requesting any missing approval.
