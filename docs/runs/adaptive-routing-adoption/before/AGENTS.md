# Solopreneur

Shared Codex guidance for independent products. Write shared instructions and preset descriptions in English; respond to the user in Korean unless requested otherwise. Follow project conventions for code identifiers.

- Begin each new task as the coordinator using `.agents/skills/solo-orchestrate/SKILL.md`; for a new product or development engagement, first route intake with `.agents/skills/solo-project-start/SKILL.md`. The primary session handles planning; the planner profile is only for bounded analysis requested by the coordinator. Keep simple question routing brief.
- Do not assign a model or reasoning effort by role, task size, or presumed cost. For an ordinary fresh specialist, omit both spawn parameters; check effective `[agents]` defaults before claiming parent inheritance. If the user explicitly specifies either setting in the prompt, pass only the requested setting(s) through a supported spawn route; a model selected without effort uses that model's default effort under Codex's documented resolution; a role-model-only setting can preserve resolved effort. Validate availability and supported combinations with the current client when possible; report an unsupported choice instead of silently substituting one. Do not treat coordinator-chosen spawn values as user choices.
- Before changing artifacts, create or resume a schema v2 run, register its plan and check/acceptance contract, and obtain an independent `plan_reviewer` review using the same inheritance rule. Keep confirmed requirements, decisions, scope, acceptance criteria, assignments, verification, and changes in `docs/runs/<run-id>/plan.md` as the task-plan SSOT. Current user direction takes precedence: update and re-review changed concerns before dependent work. Every handoff names the plan path and revision/hash.
- Delegate only needed specialists from `.solopreneur/docs/agent-catalog.md`; every specialist assignment starts a fresh clean child context and receives the plan SSOT, relevant artifact paths, ownership, acceptance criteria, and evidence paths. The primary session alone orchestrates, integrates, and writes the ledger; specialists request any extra staffing from it. Factual retrieval uses `web_researcher` or `code_explorer` and escalates judgment; observation-only browser/device checklists use `qa_runner` and cannot satisfy a final gate. Final PRDs require `product_reviewer`; design documents (including backend API/schema/security/state/error contracts) require `design_spec_reviewer` before dependent implementation; actual UI requires `design_qa` judgment from the running application or accessible implementation captures. Register product/design documents and check the matching `handoff` before assigning work that consumes them. See `.solopreneur/docs/harness.md` for commands and review freshness.
- Keep product intent in `docs/product/`, feature requirements in `docs/specs/`, technical plan/tasks in `docs/engineering/`, execution status in GitHub Projects, and implementation records in Issues/PRs. Do not present local drafts as remote state.
- Default to Next.js, React Native/Expo, Hono, and pnpm/Turborepo; build only needed platforms. Read `.solopreneur/docs/stack.md` when choosing the stack or adding services.
- Share types, validation, API contracts, business rules, design tokens, and analytics events. Keep web/mobile UI and navigation platform-specific.
- Use `.agents/skills/solo-*` for matching workflows. Follow `.solopreneur/docs/skill-catalog.md` when selecting or adapting external skills. Project instructions define local commands and exceptions. Read only relevant skills and documents.
- Run at most three specialists concurrently, plus the primary coordinator. Keep dependent work sequential. The coordinator owns integration, recorded evidence, and final completion; specialists do not recursively fan out.
- Inspect existing answers first, then ask focused follow-up questions until execution-relevant requirements are clear. Hold implementation that depends on unresolved scope, data, or behavior choices; continue independent discovery. Record confirmed answers and user-delegated decisions in the plan. Silence is not confirmation; do not re-ask settled questions or require repeated approval for authorized work.
- Use a written-specification → bounded implementation → feedback → verification loop. Review a meaningful increment before expanding it. Distinguish missing requirements, a wrong approach, missed edge cases, and tool failures before retrying; more effort cannot resolve every cause. Keep required checks and independent review even for fast iterations. Apply the effort-and-feedback reference in `solo-orchestrate`; it does not override the model/effort selection rule above.
- Prefer the simplest implementation meeting current requirements. Avoid speculative features, abstractions, or options; retain necessary validation, security, and error handling.
- Keep changes focused on the request and follow existing conventions. Remove code made unused by your changes without mixing in unrelated refactoring, formatting, or deletion.
- Define observable completion criteria and finish the requested local edits, execution, and verification. Every feature or bugfix gets an independent code gate regardless of size; scale depth to risk. Match checks to risk and actual project commands; do not repeat passing checks without cause.
- Publish, send messages, purchase, or change production data within the request and existing authorization. If further approval is needed, first prepare a reviewable result, then ask for the specific action.
- Keep secrets out of tracked files, logs, and client bundles. Confirm each service's project and environment. Use Supabase admin keys and RevenueCat secret keys only on the server.
- Report changed behavior, checks performed, and material limitations concisely. Distinguish configured connections from successful authentication and execution.
