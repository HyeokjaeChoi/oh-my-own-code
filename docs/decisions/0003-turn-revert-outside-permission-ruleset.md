# ADR-0003: Per-turn revert writes files outside the permission ruleset

**Status:** Accepted · **Date:** 2026-10-17 · **Scope:** `session.revert` and `session.revert.clear` (UI label "되돌리기" / "다시 적용")

## Problem

Reverting a turn restores workspace files from OpenCode's private snapshot (`session.revert.stage` / `.clear`). Those writes are internal to the server. They are not tool calls, so they are never evaluated against the session permission ruleset (`deny * *` base, `read_plan` / `scoped_edit` modes, path deny rules), and the deny floor and the permission overlay's path rules do not apply to them.

## Decision and rationale

File restore is app-owned, not Native's. The desktop event host keeps VCS discovery disabled, so Native's snapshot never records files. Instead the main process checkpoints the workspace before each idle send and restores from that checkpoint on revert. These writes are outside the Native permission ruleset (`deny * *` base, `read_plan` / `scoped_edit`, path deny rules); the guard is moved to the main process (`workbench-service` lifecycle), where the renderer cannot skip it:

- The workspace must be trusted, the session idle with an empty inbox (`idleIdentity`), the target a user message of that session checked with `session.message.get` (a message of another session is `INVALID_SELECTION`), and a native confirmation dialog (default deny, `confirmSessionRevert`) must be accepted for both revert and reapply. The reapply dialog warns that edits made after the revert to the same files are overwritten.
- The renderer sends only a message id. It never passes paths or a file list, and Native's `commit` is never exposed: the next prompt commits server-side.
- **Checkpoints** (`host/workspace-checkpoint.mjs`) are commits in a private git dir `<app data>/checkpoints/<workspace-id>.git`, never inside the workspace and never the user's `.git`. System git runs with a from-scratch environment: explicit `GIT_DIR` / `GIT_WORK_TREE`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `HOME` an empty app-data dir, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`, and `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c core.untrackedCache=false -c core.autocrlf=false -c core.attributesFile=/dev/null -c safe.directory=*`. The workspace's `.git/config`, hooks and `.gitattributes` filters therefore never run; file contents are read by the app and written with `fast-import`, so no content filter is involved at all. The workspace's `.gitignore` files are honored as data (standard excludes) and `.git/` is never included. Each checkpoint also records the paths it could not see (ignored paths, nested repositories, files over 5 MB or unreadable): a restore never deletes them and never overwrites such a file that exists on disk, and deletions run before writes (case-insensitive file systems). Restored files keep their permissions. Checkpoints that fall out of the 50-turn window, and dropped sessions, are pruned with `gc --prune=now`. Secrets that are not ignored (for example an untracked `.env`) are stored as plain git objects in the app-data directory (mode 0700) until pruned. Directories git could not open count as unseen (any other listing warning makes the checkpoint unavailable). A file restore needs every session of the workspace idle with an empty inbox, and is refused with CONFLICT when another session of the workspace has a newer checkpoint than the restore target. A workspace over 20,000 files or 512 MB makes the checkpoint unavailable instead of partial; git is resolved to an absolute path and run with the app-data directory as cwd.
- **Index**: git refs in the same private repo (`refs/omoc/<session>/t/<time>-<hash(message id)>`), so checkpoints survive restarts and move with the workspace. The last 50 turns per session are kept; a removed session drops its refs and a removed workspace its git dir. The operation journal still records every revert/reapply as `native.revert.stage` / `native.revert.clear` with a metadata receipt.
- **Restore** stages the revert in Native (messages), snapshots the current state as the "original", then applies only the paths that differ between the checkpoint taken before the boundary message and the current state: changed and deleted files are rewritten, files created since are removed. Every write and delete walks the path with `lstat` per component and refuses a symlink or non-directory in the path (so nothing is written or removed outside the workspace), writes to a temp file and renames, and never follows a symlink; a checkpointed symlink is restored as a link. Reapply restores the original. The first original is kept when a revert is staged again at an earlier message.
- A failure after dispatch (Native or file restore) can leave only some files restored. It is reported as `UNKNOWN_OUTCOME` and locks the session like any other unresolved effect.
- The dialog's `restoresFiles` is true only if a checkpoint exists for the boundary (or Native recorded a snapshot); the DTO's `revert.filesRestored`, `fileCount` and `files` come from the actual restore. Without a checkpoint (git missing, over the cap, first turns before this feature) the dialog says only the conversation is reverted.
- Messages are hidden by position in Native's sequence order (not by id order), reading history in pages of 100.

## Alternatives and impact

Routing the restore through tool calls (so the ruleset applies) was rejected: it would need a new tool and would make "undo" depend on the current permission mode. A renderer-side confirmation was rejected because the renderer is not trusted to gate file writes. Ignored files, files over 5 MB, and edits made outside the checkpointed turn window are not restored; the dialog says so. Enabling Native's own VCS snapshot was rejected because it requires VCS discovery in the event host.

## Revisit conditions

OpenCode gains a permission-checked snapshot restore usable without VCS discovery, or checkpoint cost on very large workspaces proves too high (the 4 s snapshot budget then makes turns restore-less).
