# Decision 0001: Workbench platform, modules, and UI ownership

Date: 2026-09-26  
Status: Architectural baseline; applicability requires the recorded independent design-spec handoff in the current run  
Decision owner: project architecture; implementation is pending

## Problem and authority

The approved [PRD](../product/prd.md) requires a local workbench that runs real project tasks through OpenCode v2, with assistant-ui and Tool UI in the renderer. The [execution contract](../engineering/workbench-architecture.md) gives a trusted local bridge authority over paths, permissions, operations, receipts, and recovery. The [UX contract](../design/specs/workbench-ux.md) and [design system](../design/system.md) define visible behavior and token ownership. Those contracts need a buildable module graph and an explicit answer to where each kind of client state lives. This ADR supplies that answer; it does not assert that a product workspace, package set, or integration has been installed.

This decision supersedes only the generic Next.js/Turborepo stack preference in the managed project guidance and the sentence in section 1 of `workbench-architecture.md` treating Next.js/React and pnpm as tentative repository preferences. It does not change the PRD, the browser/bridge trust boundary, any API or recovery semantics, security obligations, or the approved design source. If a later implementation plan needs to change those contracts, it must revise and re-review them explicitly. The task-plan source of truth for this decision is [staff-architecture revision 2](../runs/staff-architecture/plan.md).

## Chosen baseline and module graph

Use a **pnpm workspace with Nx for project graph, tasks, affected execution, and local caching**. Start with four coarse projects, each with a package name and explicit `exports`:

```text
apps/workbench-web/       React renderer; FSD layers and route composition
apps/local-bridge/        local API, persistence, policy, SDK adapters, jobs
packages/contracts/       versioned, serializable API/event schemas and IDs
packages/ui/              app-owned primitive/components source and token CSS
docs/design/tokens/       existing token source and deterministic CSS output
```

`workbench-web` may import `contracts` and `ui`; `local-bridge` may import `contracts`; `ui` may import safe contract types only where a generic component truly needs them. `contracts` imports neither application nor UI code. No browser-reachable path imports bridge source, Node built-ins, database or SDK adapters. Tool and host adapters stay inside the bridge until two independently useful consumers justify extraction. The existing SDK/UI spike remains isolated and is **evidence**, not a fifth product module or a production dependency lock. Do not create a package for every feature slice: Nx projects represent deployable/buildable boundaries, while FSD represents source ownership inside the renderer.

Project tags and [`@nx/enforce-module-boundaries`](https://nx.dev/docs/features/enforce-module-boundaries) encode the project graph: `platform:browser` can depend only on `platform:browser` or `platform:isomorphic`; `platform:server` can depend on `platform:server` or `platform:isomorphic`; `platform:isomorphic` cannot reach either platform. `scope:ui` has no runtime dependency on bridge code. Generated API types are included only through `contracts` public exports. Imports by filesystem-relative escape, path alias, `require`, dynamic import, or re-export must not bypass these checks. Audit the **resolved import graph**, including transitive dependencies and built chunks; type-only imports from server-source modules remain forbidden even if erased by TypeScript. Shared types must go through the allowed contracts public API, and its emitted browser graph must contain no server code. Workspace `exports` and `tsconfig` paths must agree, and deep imports outside a package public API fail lint.

Nx sees a whole renderer as one project, so its project-boundary rule alone cannot enforce [FSD layer and slice rules](https://fsd.how/docs/reference/layers/). Within `apps/workbench-web/src`, use `app → pages → widgets → features → entities → shared`; higher layers may import lower layers, and distinct slices on the same layer must not import one another. `app` and `shared` are the composition and common-utility exceptions described by FSD, but neither is a dumping ground for domain behavior. A slice exposes an `index.ts` [public API](https://fsd.how/docs/reference/public-api/); internal `ui`, `model`, and `api` paths stay private. Establish a repository-owned lint rule or checked import-graph script that resolves aliases and real paths, identifies the source and target slice, and rejects upward, sideways, cross-slice, and deep-public-API imports. Verify the rule with negative fixtures for each violation and an allowed lower-layer import. A convention-only folder tree is insufficient.

Illustrative renderer ownership: `pages/workbench` composes route context; `widgets/session-workspace` joins the transcript, tool activity, and sidebar; `features/send-message`, `features/decide-permission`, and `features/interrupt-run` own user intents; `entities/session`, `entities/run`, and `entities/permission` own identifiers, read models, and display mapping; `shared` owns bridge client, safe formatting, and cross-domain utilities. A widget may compose features without taking authority for their bridge mutations. This is an initial graph, not a requirement to create empty folders. Create a slice when it has a distinct public API and independent use or change pressure; split a package when independent build/release cadence, incompatible runtime dependencies, or repeated boundary violations are measured. Avoid a generic `core` package before that evidence.

Nx tasks will be `typecheck`, `lint`, `test`, and `build` only where a project has a real command. Define named inputs from tracked source, lockfile, tool config, and token source; define outputs for generated CSS and build artifacts. Do not cache `serve`, SDK host probes, migrations, permission decisions, workspace-mutating commands, or live/stateful E2E. Use **local cache only** initially; no Nx Cloud, remote service, or subscription. Cache hits are performance evidence, not test execution evidence. Untrusted imported project content must not enter the app's build configuration or local task cache; see [Nx cache security](https://nx.dev/docs/kb/cache-security). A build task should operate on reviewed source, with an isolated temporary fixture for adversarial project tests. Measure cold/warm task duration and cache correctness before adding distributed caching or more task orchestration. Nx and `@nx/vite` must be the same version, per the [Nx Vite integration](https://nx.dev/docs/technologies/build-tools/vite/introduction); exact package peers are a bootstrap check.

## Build and compatibility choices

Choose **React with Vite for the browser renderer**. The product is a local app whose trusted execution and API live in a separate bridge; it has no public SEO or server-rendering requirement. Vite gives a direct static renderer build and browser development loop without adding Next.js server/routing authority beside the bridge. Current Vite documentation describes its [Rolldown/Oxc architecture](https://vite.dev/guide/why.html); do not assume the old esbuild/Rollup implementation when tuning plugins or tests. Use a small route layer within React; choose a routing package only when navigation and URL semantics demand it. Durable router, history, query-string and persisted navigation state may carry a validated project/workspace/session **ID** and non-sensitive view state, never canonical paths, raw prompts, bootstrap secrets, approval receipts, or permission authority. Any transient one-time launcher-fragment bootstrap remains a candidate governed exclusively by the unchanged execution contract section 5: exchange and remove it immediately, and pass its history/referrer/log/preview leak checks before adoption. This is not ordinary navigation state or an authorization exception. Bridge lookup and authorization determine what an ID can open.

For the local bridge, start with **unbundled Node ESM compiled by TypeScript** and explicit package exports. A bridge bundle could simplify packaging later, but it can hide dynamic SDK imports, native dependencies, and resource paths while the host and installation form are still under test. The separate browser bundle is mandatory. Build the bridge into a clean output directory and run from that output when the host integration gate arrives; inspect runtime imports and assets. Revisit bundling if measured startup/distribution size, installation packaging, or module-loading constraints warrant it. Do not claim `tsc` output alone is a distributable product. The Node runtime and OS packaging contract remain the S-01/S-10 probes of the approved execution specification.

At bootstrap, pin a **maintained, mutually compatible set**, not an unconditional `latest`: Node runtime, pnpm, Nx/`@nx/vite`, Vite and React plugin, TypeScript, React, assistant-ui, Tool UI source, OpenCode v2 packages, state libraries, test tools, and shadcn registry dependencies. Inspect published manifests and peers, use a lockfile, and run a clean install/build/typecheck in an isolated fixture before product adoption. The [S-01/S-07 spike](../research/sdk-ui-feasibility.md) pinned React 19.2.4, `@assistant-ui/react` 0.15.22, and OpenCode packages 2.0.18 for synthetic evidence; those versions are not a verified Nx/Vite combination. The installed `@opencode/client@2.0.18` manifest requires `effect@4.0.0-rc.112` as an exact peer and declares `solid-js >=1.9.0`; these must be resolved and justified explicitly rather than described as an all-stable dependency tree or bypassed by blanket age exceptions. The SDK manifest supplies no Node engine guarantee, so Node support needs actual host and build probes. The old `@assistant-ui/react-opencode` adapter depends on a different SDK generation, so the renderer needs an app-owned v2 adapter. Upgrades are one reviewed compatibility batch, with lockfile diff, browser bundle scan, host lifecycle check, and component interaction check. Prefer security/compatibility fixes over routine version churn.

## State ownership and event flow

The bridge is the authority for all operations, permissions, policy revisions, session/run effects, process lifetime, and durable records. The renderer keeps projections, drafts, and navigation state. Assign each value one owner:

| State | Owner and mechanism | Important rule |
| --- | --- | --- |
| Ordinary read models | Desktop increment: one bounded fresh-read controller for catalog/files; no Query adoption yet | Exclude live transcript/status/permissions owned by the projection. Durable host storage remains separately reviewed; fresh reads do not prove effects. |
| Live run, transcript, tool, and permission projection | Desktop main snapshots projected through the app-owned window Zustand store; event transport is a later separately evidenced capability | One projection feeds assistant-ui and Tool UI; no parallel transcript copy in Query and Zustand. |
| Shared ephemeral UI | Window-scoped Zustand ui/draft slices with pure transitions; local state only for solely local controls | No duplicate domain owner. assistant-ui internal Zustand is an upstream dependency, not canonical app state. |
| Local form or component state | `useState`/`useReducer` and custom hooks | A hook does not itself share state between independent callers. Keep draft/form validation near its owner. |
| Stable dependency injection | React Context for bridge client, scoped store, and immutable capabilities/config | Do not route every streamed token through a broad Context provider. |
| Navigation | Pure selection transitions inside the window Zustand ui slice; validated stable IDs | Selection never grants capability or implies filesystem identity. |

This separation follows [TanStack Query defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults), [Zustand scoped stores](https://zustand.docs.pmnd.rs/learn/guides/initialize-state-with-props), and [React reducer/Context guidance](https://react.dev/learn/scaling-up-with-reducer-and-context). If Query is adopted in a future replacement increment, configure read queries' stale time and mount/focus/reconnect refetch for local bridge behavior deliberately; default stale-on-arrival and three failed-query retries are not a product policy. A bounded retry is acceptable for idempotent reads, with source-health display. Mutations use **retry 0**. The client sends the bridge-required idempotency key and expected revision; only the bridge may reconcile an uncertain effect, and the UI distinguishes `accepted`, `applied`, `effect_confirmed`, and `unknown`. Do not persist Query caches, Zustand permission state, tokens, approval decisions, or optimistic effect claims. Persist only bridge-owned records and intentionally saved user drafts under the existing retention contract.

The app-owned event adapter keys data by install epoch, project, workspace, session, and run. It subscribes first, captures the last durable app cursor, reads `GET /snapshot`, replays `GET /events?after=`, de-duplicates by event ID/sequence, and compares revisions and source health. A duplicate or lower revision cannot roll state backward. The adapter batches high-frequency token deltas for rendering while applying identity, status, and permission changes promptly; an initial target is at most one visible transcript commit per animation frame, with a measured backlog/latency threshold before tuning. A gap is shown as `history_gap`; no invented transcript fills it. A disconnect marks live state stale, disables stale tool/permission actions, and triggers re-subscribe and reconciliation. Keep session-scoped draft, approval, and pending action maps separate so tab switches cannot leak actions between sessions. Assistant-ui consumes this projection through its external runtime; Tool UI renders only schema-validated tool results dispatched from that same runtime. Unknown tools use the safe generic card. A card action carries original session/request/policy identifiers back to the bridge for fresh validation. This preserves the approved [assistant-ui / Tool UI division](../design/specs/workbench-ux.md#assistant-ui와-tool-ui의-경계).

The event adapter fetches its reconciliation snapshot directly through the transport; it does not retain a second live snapshot in Query. Metadata invalidation may notify Query, but live fields remain exclusively in the external projection. Components select from that owner and never copy authoritative fields into a local UI store. Abort in-flight reads and discard callbacks from a prior scope/epoch during teardown. The transcript projection releases listeners and buffers when its owning session scope is disposed, while the bridge retains actual execution lifetime.

## Components and token source

User clarification on 2026-10-03 supersedes the former Base UI default: **Base UI, Radix and shadcn are optional candidates, not mandated or user-approved dependencies.** Choose native/owned controls when adequate. Compare complex interaction requirements, keyboard/focus behavior, accessibility, assistant-ui/Tool UI composition, token/style ownership, dependency cost and maintenance before selecting library primitives. Any selected copied source belongs under `packages/ui` with pinned provenance, license and peer compatibility evidence. Validate aliases, exports and actual interactions. Do not mix primitive implementations casually within one interaction pattern. Library adoption does not establish visual or accessibility quality.

The repository's 163-token [manifest](../design/tokens/manifest.json), deterministic CSS, and six component families remain the visual source. Map shadcn variables/classes onto semantic and component tokens rather than replacing the token hierarchy with registry defaults. Check light/dark and Korean text, 200% zoom, 320px layout, focus visibility, reduced motion, and status/permission language against the approved design spec. `assistant-ui` owns thread/composer behavior and `Tool UI` owns validated tool cards; do not replace either with generic shadcn chat or approval widgets. The existing Tool UI spike found that parser acceptance did not prove safe navigation, so interaction and href sanitization need browser checks. A copied component is accepted only after its actions, focus restoration, and accessible name fit the product workflow.

## Alternatives, costs, and reversal

| Choice | Alternative and reason deferred | Cost/reversal condition |
| --- | --- | --- |
| pnpm + Nx | pnpm + Turborepo is smaller to configure, but its task graph alone does not supply the selected Nx project-boundary path. Plain pnpm scripts also work at this size but need custom affected/task graph handling. | Nx config and cache add maintenance. If task graph and boundary value fail to justify that cost after first two product increments, keep pnpm packages and replace Nx tasks with scripts/Turbo while retaining the resolved-path FSD checker. |
| Vite renderer | Next.js offers SSR, server routing, and full-stack conventions the local renderer does not currently need; adopting it would add another server surface. | Revisit if a confirmed delivery mode requires server-rendered pages, web hosting, or framework routing capabilities. Keep the browser/bridge contract independent of the renderer tool. |
| Unbundled bridge | A bundled server can simplify shipping, but early bundling obscures dynamic/native resources. | Revisit after S-01 and S-10 measure packaging, startup, and native import behavior. Keep bridge APIs and contracts stable during a build-tool change. |
| Zustand app/domain projection + bounded fresh reads + solely local React state/Context | Query/XState remain deferred alternatives; separate custom canonical stores or other global state frameworks are excluded. | Replacement must remove the previous owner atomically; never retain duplicate caches/stores for the same data. |
| Component primitives: selection pending comparison | Native/owned controls, Base UI, Radix and shadcn source are candidates. Complex custom overlays create focus/accessibility maintenance obligations. | Select the smallest suitable implementation after a focused interaction/compatibility probe; no library is mandatory. |

The dominant risks are boundary bypass through aliases/transitive imports, duplicate live state, stale approval actions, cached or replayed side effects, package peer drift, and copied-source accessibility regressions. The gates below target those failure modes. There is no promise of OS-level isolation from these library decisions.

## Implementation gates and evidence

1. **Bootstrap:** record Node/pnpm and package peer manifests, lockfile, exact Nx/Vite/plugin versions, scripts, task inputs/outputs, and clean fixture build/typecheck. Demonstrate local cache hits only for pure tasks; show stateful commands uncached. No installation is asserted by this ADR.
2. **Boundaries:** run positive and negative import fixtures for Nx project tags, renderer FSD direction, same-layer slice isolation, public APIs, aliases, relative escapes, dynamic imports, and re-exports. Inspect emitted browser chunks for Node built-ins, bridge, SQLite, OpenCode host SDK, provider credentials, and bootstrap secrets; any occurrence fails the gate.
3. **State:** use synthetic event sequences for duplicate/out-of-order events, lower revisions, session switch isolation, disconnect/reconnect with gaps, batch latency, and stale approval. Verify Query refetch cannot report a mutation success, mutation retry is zero, and bridge revisions/receipts are the only effect authority. Live SDK event behavior remains a separate S-01/S-09 gate.
4. **UI integration:** in a browser, prove assistant-ui external runtime dispatches Tool UI cards and safe fallback, then exercise canceled/reconnected actions, keyboard and screen-reader flow, focus return, narrow width, light/dark, and reduced motion with token mappings. Isolated SSR/type checks from the spike do not satisfy this gate.
5. **Release decision:** require the existing S-01–S-10, security, recovery, design QA, and product acceptance evidence before calling the workbench shippable. Static architecture review approves this decision's consistency only; it does not prove runtime enforcement, SDK compatibility, or a finished app.
