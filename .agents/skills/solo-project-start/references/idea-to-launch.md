# Idea to launch route

Use only as far as the requested endpoint. A supplied current brief or PRD can enter at the next missing stage after its required independent review and clear user adoption; do not demand a retroactive one-pager or duplicate approval for an exact version the user already adopted. If the supplied artifact is unvalidated or its approval is unclear, resolve that decision before dependent work. `$solo-orchestrate` creates a run and reviewed plan SSOT for each substantive stage; keep the product artifacts and decision evidence linked from it. Route unspecified specialist model and effort under [adaptive-routing](../../solo-orchestrate/references/adaptive-routing.md), preserving exact user choices and explicit inheritance/default instructions. Run independent document gates before handing a contract to a dependent stage.

## 1. Frame and research the opportunity

Ask for the idea in a few sentences, the intended user, the pain or desired outcome, and why now. Grill unclear claims with focused follow-ups: current workaround, reachable audience, strongest alternative, evidence already held, and what result would change the founder's mind. Avoid inventing interviews, demand, market size, or willingness to pay. Research only the consequential unknowns. Use `$solo-evidence-research` and `web_researcher` for dated source facts, `product_research` for synthesis and competing hypotheses, and `$solo-product-spec` for product judgment. Distinguish observation, inference, and assumption.

Create a concise `docs/product/opportunity.md` decision one-pager: problem/user, current alternatives, differentiated wedge, evidence with source/date, assumptions and counterevidence, smallest validation test, plausible MVP boundary, success/stop signal, effort/cost range if defensible, key risks, and a clear pursue / revise / stop recommendation. Optimize for a founder decision, not an exhaustive market report. Register it as a product artifact and obtain independent `product_reviewer` judgment. Present the reviewed exact version and ask whether to proceed to PRD. **Do not start PRD drafting until the user explicitly approves this decision checkpoint.** If the endpoint is only exploration, stop after the one-pager and decision request.

## 2. PRD and coordinated domain specs

After one-pager approval, use `$solo-product-spec` to draft the PRD in `docs/product/` or `docs/specs/`: intended outcome, journeys, non-goals, acceptance criteria, primary metric, privacy/data needs, and release boundary. Register it, get independent `$solo-product-review`, show its exact version and consequential tradeoffs, then ask for explicit approval before assigning domain specs. If review or user approval changes requirements, revise the plan and PRD and refresh review before proceeding.

After PRD approval, write only the relevant specs in parallel, with separate owned paths and a common PRD/version: design and UX, engineering/API/data under `docs/engineering/`, test and acceptance, analytics, monetization, release/operations, and growth when applicable. Use the corresponding existing skills and fresh specialists; do not launch every role by default. The coordinator reconciles shared interfaces, events, terminology, dependencies, contradictions, and cost/scope into a versioned spec index or decision record that links the exact domain artifacts. Obtain the required independent product/design document reviews, versioned user approval evidence, and `handoff` checks. Present the integrated set and unresolved tradeoffs for **explicit user approval of that exact version** before dependent design production or coding. A later material change reopens only affected contracts and approval.

## 3. Design after spec approval

Choose the design tool with the user from the actual work and available access; Figma, Penpot, and OpenDesign are examples, not defaults or presumed connections. Record the chosen tool and source of truth. Inspect available plugins/MCPs and the current client; distinguish configured endpoint, authenticated account, and a successful small read against the intended file/project. If access is missing, configure the chosen connection when possible under existing authorization, request only the user action needed for login/account consent, and verify a read before claiming access. Hold tool-dependent design production until that read succeeds; independent research can continue. Do not silently switch tools, create paid accounts, or paste secrets into config. The toolkit currently includes an optional Figma preset; use `solo.py mcp-enable <project> figma` only when Figma was chosen and needed. For another tool, consult current official setup instructions and existing connectors before adding configuration.

Check for a current design system in `design.md`, `docs/design/`, code tokens, or accessible design files. Ask for the existing system or a preferred open reference when absent, and decide with the user whether a new system is needed. Preserve an approved system. Use `$solo-design-research` on the agreed flows; use Mobbin, Lazyweb, or comparable sources only when actually available and authorized, with dated evidence and clear licensing boundaries. Then use `$solo-design-system` to create or adapt the contract, register design artifacts, obtain `$solo-design-spec-review`, and pass the design-spec handoff before consuming screens are implemented. Design documents are distinct from rendered-UI validation.

## 4. Build, verify, release, and learn

Route reviewed vertical slices through `$solo-engineering-plan` where architecture warrants it and `$solo-implement` for coding. Use `$solo-tdd` only where meaningful regression behavior warrants it. Verify against acceptance criteria with the project's format/lint/type/unit/integration checks as applicable, plus actual browser/device E2E for critical user journeys when available. Collect observation via `$solo-qa-run`; independent `$solo-code-review` and `$solo-design-review` make final code and rendered-UI judgments. Instrument agreed events with `$solo-analytics-instrumentation`; cover payments, store assets/ASO, and marketing only if in scope.

For an authorized launch endpoint, use `$solo-release` with environment, rollback, and direct release evidence. Follow with `$solo-monitoring` and `$solo-analytics-experiment` on release health, activation/funnel/retention or agreed business metrics, stating baseline, denominator, time window, and uncertainty. Report the first measured iteration decision. If live traffic, accounts, or elapsed observation time are missing, deliver the measurement plan and explain what remains unobserved rather than claiming post-launch outcomes.
