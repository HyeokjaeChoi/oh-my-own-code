# Independent entry plan review

Classify the work before selecting gates. `major` covers initial new-feature introduction, substantial refactoring, or a change to product scope, architecture, runtime ownership, security boundaries, or data/API contracts. Obtain independent plan review and applicable design-spec review at that initial entry. `routine` covers implementation, fixes, small refactors, test repairs, and input preparation within the existing accepted scope and design. Use concise plan -> edit -> appropriate checks -> separate independent code review -> integrate; do not add plan/design approval rounds for each ordinary change. If routine work crosses a major boundary, record the reason and classify the changed concern as major before dependent work. Do not create a new major classification merely because code or hashes changed. Preserve explicit additional reviews, user approvals, decision blockers, final code-review independence, and required evidence. Records without a work classification retain their historical major policy until an explicit active-run classification; never rewrite terminal records.

Use an independent `plan_reviewer` routed under the shared adaptive-routing reference, preserving exact user choices and explicit inheritance/default instructions. Review the user request, material constraints, relevant product/repository evidence, proposed plan, and intended completion boundary. Do not author the plan being reviewed or restart the full workflow. The coordinator saves this read-only review.

First compare the plan with the latest explicit user outcome and requested deliverable. Verify target platforms, runtime/process ownership, deployment/package form, UX form, and important exclusions are preserved; do not let an earlier provisional assumption or detailed solution review replace this fit check. Then compare the plan and contract `decision_register` with current user direction. Check that each consequential decision is labeled `open`, `assumption`, `confirmed`, or `delegated`, carries source/authority and impact, and blocks dependent phases while unresolved. Confirm that a choice was not silently promoted because a research report exists, specialists agreed, or implementation has begun. The register is an enforcement aid, not proof of completeness: identify consequential decisions from the user request even when they are omitted. A user's explicit correction supersedes the prior plan and requires an updated plan/register; entry review is repeated only for major changed concerns or an explicitly required gate.

Only after goal and decision fit, check acceptance criteria, supported assumptions, appropriate release scope, and a feasible smaller alternative where relevant. For consequential platform/runtime/security-boundary choices, require credible alternatives compared against explicit criteria and tradeoffs, a reasoned recommendation or an open decision with dependent work held, and user delegation when the coordinator is to choose. A technology list or successful prototype alone is not an ADR or authorization. Routine decisions within an approved architecture need no duplicate analysis. Then inspect affected concerns: user states and accessibility for design; contracts, dependencies, migrations, and failures for engineering; entitlement lifecycle for monetization; evidence and denominators for analytics/growth; artifact, target, recovery, and observation for releases. Verify that each claimed test or evidence source actually covers the runtime, OS, security boundary, and target behavior being claimed. A browser bridge probe cannot prove desktop sidecar ownership or process cleanup; static compatibility review cannot prove packaging or runtime enforcement.

Verify the task-plan SSOT at `docs/runs/<run-id>/plan.md`: current revision, confirmed requirements and decisions, source/delegation for consequential assumptions, open questions and dependency holds, and change history. Questions that affect the next implementation step must be answered or explicitly delegated before that work starts; silence is not confirmation. Check current user direction against the document and every handoff's plan path/version. Avoid requiring further user approval for an already authorized, sufficiently clear task.

Each assignment needs an owner, inputs, bounded outputs/files, dependencies, and evidence that can establish completion. Confirm that code/design review is independent of implementation, tests exercise the intended behavior, and the plan distinguishes local preparation from authorized external actions. Identify missing access without turning it into approval for unrelated work.

PRD delivery needs independent `product_reviewer` review. New or materially changed design documents need `design_spec_reviewer` review at major entry. Routine edits using accepted contracts need no repeated document approval. Require document registration and the corresponding `handoff` check before assigning consumers; preserve separate actual-UI QA and fresh final reviews after implementation/checks.

When `NO-RUN`, missing capability, or repeated non-advancing corrections occur, require classification of requirement uncertainty, wrong approach, implementation defect, and tool/access failure before another retry. Additional effort alone is not a corrective strategy.

Return one of `pass`, `changes_requested`, or `blocked`, with concrete findings, impact, and required corrections. A small task needs only a short review. Mark preferences as optional; do not invent blockers to fill a checklist. Revised plans need review of their changed concerns. Record the exact plan path/version and do not reuse a verdict after its scope changes. For the compact micro-change path, confirm the 1–2 file, no-behavior-change criteria; otherwise return `changes_requested`.

The coordinator registers the actual report using the harness `review` command with gate `plan` and reviewer `plan_reviewer`. A model verdict is not user authorization to purchase, publish, communicate externally, or change production data.
