# Clarification and task-plan SSOT

Classify the work before selecting gates. `major` covers initial new-feature introduction, substantial refactoring, or a change to product scope, architecture, runtime ownership, security boundaries, or data/API contracts. Obtain independent plan review and applicable design-spec review at that initial entry. `routine` covers implementation, fixes, small refactors, test repairs, and input preparation within the existing accepted scope and design. Use concise plan -> edit -> appropriate checks -> separate independent code review -> integrate; do not add plan/design approval rounds for each ordinary change. If routine work crosses a major boundary, record the reason and classify the changed concern as major before dependent work. Do not create a new major classification merely because code or hashes changed. Preserve explicit additional reviews, user approvals, decision blockers, final code-review independence, and required evidence. Records without a work classification retain their historical major policy until an explicit active-run classification; never rewrite terminal records.

Read existing context and answers before asking. Clarify the user outcome, intended users, included/excluded behavior, constraints, acceptance criteria, and dependencies to the level needed for the next execution step. Ask focused follow-ups until consequential uncertainty is resolved by an answer or explicit delegation. Do not require perfect knowledge of future phases. Proceed on settled details and documented delegated choices; never interpret silence as confirmation.

While a blocking question is pending, hold only work that depends on its answer and continue independent research. Record each open question, its impact, and the work it blocks. Do not repeatedly ask about settled preferences or invent a user approval requirement for an already authorized task.

The coordinator creates a schema v2 run, then saves its canonical execution plan at `docs/runs/<run-id>/plan.md` and a `contract.json` with acceptance IDs, exact named checks, relevant document versions, approvals, and environment file paths. A delegated read-only planner returns content for the coordinator to persist. Scale length to the task; include:

- revision/date and status;
- confirmed outcome, requirements, scope/non-goals, and acceptance criteria;
- decisions with their user/context source, delegated choices and rationale, and consequential assumptions;
- a `decision_register` in the schema-v2 contract for consequential decisions, using explicit `open`, `assumption`, `confirmed`, or `delegated` status; record source/authority, impact, and which supported handoff phases (`research`, `implementation`, `review`) are blocked;
- unresolved questions and their dependency holds, or an explicit statement that none blocks execution;
- ordered assignments with owned files, inputs, outputs, dependencies, and meaningful verification;
- for iterative work, the first reviewable increment, the uncertainty its feedback resolves, and the failure evidence that would require a different approach; scale this to the task rather than adding a separate ceremony;
- ownership table mapping each role to its owned path globs (advisory, with packet ownership for handoffs);
- canonical product/design/architecture links and required independent reviews;
- change history identifying what changed and why.

This file is the task-plan single source of truth (SSOT). Product requirements and design contracts retain their domain ownership; link them rather than copying an independently maintained execution plan into chat, issues, or architecture documents. Every specialist handoff names the current plan path and revision/hash. On resumption or compaction, recover from that plan and the run ledger, then reconcile new user input.

Current user direction always takes precedence over the saved plan. When requirements, decisions, scope, or sequencing change materially, update the plan and re-register it; obtain an independent entry review only when the change is major or an entry gate is explicitly required. A changed plan hash invalidates old plan approval and affected downstream evidence. Current opt-in scoped checks can survive plan wording or unrelated check changes when their declared binding remains identical; unscoped checks keep full plan/source/contract freshness. Define independently executable UI scenario families before attempting state-specific reuse; unknown dependency closures require full checks. Keep execution progress in the ledger or a separate outcome record so routine progress updates do not silently rewrite the reviewed contract.

For each consequential choice, distinguish an explicit user confirmation, user-delegated choice, supported temporary assumption, and unresolved question. `open` blocks at least one phase. An `assumption` is usable only in phases it does not block, with a stated safe/reversible rationale; if the assumption changes platform, runtime ownership, permission/security boundary, deliverable type, or release target, block dependent execution. `confirmed` and `delegated` entries need an authority/source and a resolution record, and have no blockers. Keep user wording concise but traceable. Update both the plan and register when the user corrects scope or direction; a new instruction resolves the corresponding register entry only when its authority and meaning are explicit. Never label an unresolved choice as selected merely because a comparison exists or specialists agree.

Before implementation that commits to a consequential platform, desktop shell, runtime/process model, module/build architecture, or security boundary, compare credible alternatives against the actual requirements. Record decision criteria, constraints, tradeoffs, reversibility/migration cost, evidence, recommendation and any unresolved risk. A technology list is not a comparison; research or reviewer consensus is not user delegation. Keep the decision open and block dependent implementation when authority to choose is absent or the evidence is insufficient. Routine changes already covered by an approved architecture contract need no duplicate comparison.

Before every dependent handoff, compare the register against the latest user message and current task goal, prepare a phase-specific packet, then recheck the register and the current recorded plan at dispatch, including its independent pass only when the work class or an explicit requirement calls for it. The local gate blocks registered decisions only; it cannot detect a missing or inaccurately classified entry. The coordinator checks register completeness and goal fit in routine work; an independent plan reviewer also checks it at major entry. `release` is not currently a supported handoff phase; until the CLI adds and tests it, route release execution and review through supported implementation/review phases and retain any separate release approvals.

User confirmation means supported answers or delegation already present in the conversation; independent plan review is peer review. Neither requires an extra user sign-off unless a specific unresolved decision or external action actually needs it.
